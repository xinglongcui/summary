TPU 推理外部化：InferenceX、TorchTPU、MoE 通信与缓存协同设计

原文：TPU Inference Externalization Full Steam Ahead - InferenceX

1. 文章信息与选文原因

原标题：TPU Inference Externalization Full Steam Ahead - InferenceX；译名：《TPU 推理对外开放全速推进——InferenceX》。副标题译意：InferenceX、最高提升 50% 的单位成本性能、TPU 软件栈快速开放、Ironwood、TPUv8i 与 CUDA 生态竞争。作者 Alec Ibarra、Cam Quilici、Bryan Shan 等七人（公开页面仅列前三人）。发布日期 2026-09-07。原文标记 Paid，但主要技术正文公开可读，完整 BOM/TCO 付费章节不可访问。2026-11-10 核查官方 Sitemap 最新为 11 月 7 日文章，已在第 23 期分析；第 24 期 URL 台账中 9 月 10 日及其后相关文章已分析，故选择 9 月 7 日未分析文章。与 11 月 5 日 Ironwood 文章为不同 URL，不重复。

2. 原文翻译与中文转述

导语：Google 十余年来在自家搜索、广告、YouTube 与 Gemini 使用 TPU，真正悬而未决的问题是外部客户能否在开源模型与熟悉的推理引擎上获得可竞争的单位成本性能。作者公布 TPUv7 Ironwood 的 InferenceX 第三方预览测试，认为部分场景性能/美元领先，但软件生态尚需完善。

InferenceX Official Preview（TPUv7 与 Blackwell 对比）：首个模型 Qwen3.5-397B，FP8、单 Token 预测、聚合式 serving，主要基准 8k 输入/1k 输出。100 tok/s/user 时 TPU 每百万总 Token $0.181，B200 $0.222，B300 $0.276；20 tok/s/user 时每芯片吞吐 9364、8903、8925 token/s。256 并发时 TPU 平均 TTFT 5.41s，B200 3.75s，B300 2.40s，证明最高性价比点不等于低时延点。

Apples to Bananas（非同条件比较）：Google 内部已有 P/D 解耦，但当时外部 TPU 栈尚未优化。GB300 NVL72 在部分端到端时延区间相较 TPU 聚合式 serving 有约 30% 单位成本性能优势；作者预计 TPU 外部化后缩小差距，这不是已证实结果。

TorchAX 到 TorchTPU：旧版 TorchAX 通过 __torch_dispatch__ 将 PyTorch ATen 转为 JAX，并通过 jax.jit/XLA 编译，KV Cache 需函数化。SGLang-JAX 是独立 JAX-native serving 引擎。新 TorchTPU 用 PyTorch PrivateUse1 暴露 device='tpu'，通过 dispatcher、TorchDynamo/AOTAutograd、FX、StableHLO、XLA 编译，Pallas/JAX 专用 Kernel 仍保留。所谓原生是框架和分布式 API 原生，不意味着 Inductor/Triton 取代 XLA。文章写作时为 private beta，10 月开源只是计划。

DP Attention 与 EP：Qwen3.5 的 32 Query Heads、2 KV Heads 在 TP8 下需要复制 KV Head；DP8 Attention + EP8 让不同设备持有不同请求的 KV，512 routed experts 跨设备分布。GroupedGEMM 前 AllGather Activation/路由元数据，后 ReduceScatter 返回。合并专家 ID 与权重 AllGather 的 PR 在 DeepSeek-V3 微基准每层节约约 80μs，58 层算术累计 4.64ms，但不是端到端实测收益。SparseCore ReduceScatter、双缓冲与 Die 内优先规约，在指定 8k1k 负载吞吐提升 4.1–14.2%，小消息卸载也可能因开销反而变慢。

MoE Kernel：针对 ragged token groups，减少 padding、GroupedGEMM triple-buffer 权重、将 token permutation/gather 移到 SparseCore、低 batch 专用 permutation、组合 expert ID/token index 排序键。不同 PR 报告吞吐 +12%、小 batch +5.1–7.3%，基线不同不可叠加。

Gated DeltaNet：GDN 状态递归更新，代数重排允许 MXU 计算旧状态投影、VPU 并行更新状态，另通过寄存器活跃区间压缩、异步 DMA、Conv1D/GDN 融合优化。GDN v3 Kernel 层面 Decode 1.41×、Prefill 1.60×、混合 2.14×，不是整模型加速比。

Hybrid State 与 HBM：GQA KV 随上下文增长，GDN 状态每请求固定规模。紧凑分配在指定配置回收约 76GiB HBM、attention block pool +71%；BF16 存储状态、VMEM 内 FP32 算术减少内存。混合 Prefix Cache 需同时保存 KV 和 GDN checkpoint，checkpoint pool 与紧凑分配有容量取舍。

Paged Attention 与低并发：按活跃请求数调整 metadata bucket，减少无效专家执行。将 Sequence 放到 128-lane 轴使指定配置 KV 页从 5141 增至 10283，但低并发每 Token 延迟约增加 3%；高并发缓解 KV 排队。分离 16k KV fetch block 与 4k compute block 在 Qwen3-0.6B 上使 Decode 64.9k→96.3k token/s，不是 Qwen3.5-397B 结果。

系统协同与互联：Ironwood 每芯片两个独立逻辑计算 Die，256×256 MXU 相比 128×128 MAC 数量为四倍；未重排时 128/64 Head Dim 可能只有 50%/25% 阵列利用率。ICI 采用 3D Torus，4×4×4 的 64 芯片 Cube 经 OCS 扩展，文中描述 9216 芯片 Superpod。TPUv8i Boardfly 为后续路线：更扁平的高 Radix 网络，文中约 16→7 hops、19.2Tb/s ICI、384MB SRAM，需与 Google 官方规格单独核验。

后续路线：MTP speculative decoding、P/D disaggregation、TPU-Sync 零拷贝 KV 转移、Host DRAM/NVMe offload、Mooncake Store、AgentX 多轮场景。Agent 工作负载有长上下文、高 Prefix 复用与子 Agent 突发；预计 TPUv7 追平 GB300、TPUv8i 挑战 Rubin 都属于作者判断。原文从 TPU Cost Effective Total Cost of Ownership 章节开始进入付费墙；未阅读其 BOM/TCO 明细。上述为按公开章节的中文转述，不是逐字全文翻译。

3. 核心论点与关键数据

100 tok/s/user：每百万总 Token TPUv7 $0.181，B200 $0.222，B300 $0.276；20 tok/s/user：每芯片 TPU 9364、B200 8903、B300 8925 token/s；256 并发平均 TTFT：TPU 5.41s、B200 3.75s、B300 2.40s。GDN 状态紧凑分配节约约 76GiB HBM；指定 KV 页布局 5141→10283；特定小模型 Decode Kernel 64.9k→96.3k token/s。所有数字受模型、精度、TCO、并发、延迟和测试基线限制，不能混为同一端到端结果。

4. 技术机制与硬件、互联、推理架构影响

MXU tile 与 Head Dim、Expert Width 的形状匹配决定实际计算效率。GQA KV 与 GDN recurrent state 的分配和页布局决定 HBM 有效容量。DP Attention 将请求历史局部化，EP 仍需跨 ICI AllGather/ReduceScatter；短消息启动时延、SparseCore offload 门槛、Die 内外规约顺序与双缓冲可能比峰值 Tb/s 更关键。Torus 多跳与 Boardfly 高 Radix 优劣必须在同消息尺寸、注入率、P99 下比较。P/D 分池和 KV Offload 增加网络、Host DRAM、NVMe 的流量与尾延迟约束。对交换芯片 PRD 应补充小消息 Collective 延迟、拥塞、Buffer、重传与 Token/s/user SLA 联合验收，不能仅看原始端口带宽。

5. 事实、作者判断、独立推断

【原文明确事实】文章发布日期、Paid 标记、公开测试数据、文内引用的 PR 微基准及软件路径；这里的“事实”是原文可核对报告值，不代表独立复测。【作者预测/判断】TorchTPU 迅速成熟、进入主流模型 day-0 支持、TPUv7 优化 P/D 后与 GB300 全 Pareto 竞争、TPUv8i 对 Rubin 竞争力、CUDA 护城河削弱。【独立推断】模型形状、Collective 小包、KV Cache 管理可能对有效 Token 成本的影响超过单纯峰值 FLOPS；需要通过相同 SLA 的实测验证。
