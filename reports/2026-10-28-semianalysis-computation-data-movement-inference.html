SECTION 1

编排器通过队列向 Worker 池分发请求

Orchestration delivers requests via queues into pools of workers

请求进入系统时携带新 Token、可复用上下文、SLO 与会话状态，并非天然已经组成 Batch。调度器按长度与目标延迟将请求放入 Prefill、Midfill 或 Decode 池；Continuous Batching 允许请求动态进出。KV 可以从生成它的 Worker 脱离，由共享存储与网络交付给下游。Prefill/Midfill 的工作量相对可预测，Decode 输出长度则具有随机性。作者将服务视为多个独立节奏的 Worker 经状态迁移连接的循环，而不是单机上一次前向传播。

原文位置：SemiAnalysis §1 · [S1]

SECTION 2

KV 状态以不可变数据块形式迁移

KV state moves as immutable blobs

作者建议把系统提示词、历史对话、工具结果与新生成 Token 对应的 KV 组织成可共享的逻辑 Blob；新轮次在既有前缀上追加版本，分叉可回退后重建。活跃数据驻留 HBM，较热的共享前缀可驻留 CPU DRAM/网络内存，冷数据放 SSD 或由更小的文本重算。CPU 内存承担元数据、暂存和回退；RDMA 可减少进入 GPU 时的额外复制。这里的“不可变”指逻辑缓存对象/版本管理，不等于 Decode 内核不会写新的 KV 页。

原文位置：SemiAnalysis §2 · [S1]

SECTION 3

Prefill、Midfill、Decode 具有不同运行区间

Prefill, midfill, and decode create distinct operating regimes

Prefill 处理大块新输入，权重重用充分，往往偏计算受限；Midfill 在长前缀上追加少量新 Token，既有 KV 扫描又有批量 GEMM，属于混合瓶颈；Decode Attention 每步读取各请求私有 KV，长上下文下偏内存带宽受限；Decode Experts 只消费本步 Activation，不需要历史 KV，因而可跨请求汇集 Expert 工作，但小 Batch 下权重复用概率低。作者把 Decode Attention 与 Decode Experts 分开，是为了避免将不同数据局部性混成一个“Decode”。

原文位置：SemiAnalysis §3 · [S1]

SECTION 4

MoE Prefill 层的数据流

Flow through an MoE prefill layer

Attention 与共享变换后，Router 对每个 Token 选取若干 Expert；先按 Token 顺序产生稀疏路由记录，再按 Expert ID 排序/分桶，形成可批量执行的 Expert 输入。Dispatch 把 Activation 发往目的 Expert，Expert 权重只需加载一次处理同桶 Token；Combine 将输出恢复 Token 顺序并加权归并。作者提出 Scale-up 上的 Memory-mapped Queue 作为一种潜在低开销实现，不能把它视为所有 NVLink 系统已经采用的标准协议。

原文位置：SemiAnalysis §4 · [S1]

SECTION 5

MoE Decode 层的数据流

Flow through an MoE decode layer

每步通常只有一个或少量候选 Token；Attention 扫描旧 KV 并追加新 K/V，Router 选择少量 Expert，Expert 返回后归并、投影进入下一层。Attention 的历史状态规模大，而送往 Expert 的 Activation 较小。由于每步可合并的 Token 少，Expert 权重加载难以被摊薄。该阶段同时要求大规模 KV 读带宽与低延迟 Expert Dispatch/Combine。

原文位置：SemiAnalysis §5 · [S1]

SECTION 6

Midfill 是独立的运行区间

Midfill is a distinct operating regime

作者引用 AgentX 轨迹，指出长对话可能有数十万到百万 Token 的旧上下文，而新追加输入常在约 50—5,000 Token 范围。Midfill 既能利用新 Token 形成 Expert Batch，又要读取巨大旧 KV；持续时间与 Decode Batch 不同。将它简单当作短 Prefill 或大 Decode，会误判资源需求与流水线占用，因此可能值得设置专门的 Midfill Worker 池。

原文位置：SemiAnalysis §6 · [S1]

SECTION 7

模型是重复 Layer Group 的高层堆栈

The model is a tall stack of repeating layer groups

模型参数量不直接决定部署方法；应按重复 Layer Group 分析，其中可能包含 Full Attention 与若干 Local/Linear/Delta/Selective Attention。作者用宽而薄的“薄饼”表示每组层内并行宽度、沿深度方向重复的结构；这一比喻强调一组映射与编译计划可跨多组复用，并非要求物理封装也采用该形状。

原文位置：SemiAnalysis §7 · [S1]

SECTION 8

并行方式应沿最窄的数据流切分

Parallelism should partition the narrow dataflows of the model

PP 沿层深度分割，跨 Stage 传相对小的 Activation；TP 用于宽矩阵或 Attention 分区，需要 Reduction/Collective；EP 将彼此独立的 Expert 权重分散到 Peer Set，交换路由 Activation。作者反对将 TP 机械应用到所有小 Expert GEMM：通信代价可能超过算术收益。Stage 是否可放入 Scale-up 域，还要满足权重、Batch、工作缓冲与余量的快存容量约束。

原文位置：SemiAnalysis §8 · [S1]

SECTION 9

逻辑加速器节点

A logical accelerator node

作者以约 16 加速器的 Peer Set 作为概念示意：每颗加速器有计算与本地快存，经低延迟 Scale-up 互联；CPU 管协调，NIC 管外部连接。文中画成 Ring 只是示意平等 Peer，明确不主张真实拓扑必须是 Ring。可选 Hub、Switch、Torus、Hypercube 或分层 Fabric；关键是把高频操作保留在确定性强的本地域。

原文位置：SemiAnalysis §9 · [S1]

SECTION 10

多个节点构成机柜

Nodes stack to make racks

一个 Rack 可是整柜 Scale-up 域，也可以有多个局部 Scale-up Island、独立 Rack Backbone 或 Pipeline Stage。若 NVL72 类方案已覆盖整柜，则不一定再需要独立的 Rack 中间互联层。作者区分两个扩展问题：单个 Worker 能否容纳模型，以及服务通过增加 Worker 数量能否扩容。

原文位置：SemiAnalysis §10 · [S1]

SECTION 11

Layer Group 按时间复用节点资源

One layer group reuses the node over time

同一组 GPU 的计算单元、内存通道与缓冲可在 Attention、Shared Transform、Expert GEMM、Combine 之间分时复用。静态图上部分单元闲置不等于机器设计浪费；真正要看连续操作间的切换、预取与同步成本。也因此，不能把单个算子峰值利用率直接当作端到端 Token 性能。

原文位置：SemiAnalysis §11 · [S1]

SECTION 12

在流量最窄的位置划分吞吐边界

Put throughput boundaries where the flow is smallest

作者核心规则：高频、突发、对同步敏感的 Attention/Expert 内环应尽可能留在强 Scale-up Fabric；较小的 Pipeline Activation、较低频且可摊销的 KV Blob 迁移可走 Scale-out。EP All-to-All 的难点不仅是字节量，更是目的端数量、同步与小消息开销。即使额外 100ns Hop 对大 KV 搬运不明显，也可能影响亚微秒级 Expert 操作。

原文位置：SemiAnalysis §12 · [S1]

SECTION 13

尽量以 Layer Group 为 Pipeline 单位

Pipeline by layer group where practical

把一整个重复 Layer Group 放在同一 Stage，便于编译、布局、监控、故障恢复和跨 Stage 复制；但并非绝对规则。若内存或性能需要，也可以在 Group 中间切分，只是部署与调度复杂度提高。

原文位置：SemiAnalysis §13 · [S1]

SECTION 14

Pipeline 深度受 KV Cache 交叉点限制

Pipeline depth ends at the KV-cache crossover

理想情况下权重每 Stage 约 W/P；但要维持 P 个 Stage 同时工作，活跃请求数也上升，各 Stage 需要为多个并行流保留其负责层的 KV，因此 KV 内存不按 W/P 同步下降。文章以 70kB/Token、200 万 Token 总活跃上下文估出约 140GB KV，双缓冲约 280GB，叠加权重与余量给出每 Stage 400—500GB 快存的 2027 设计参考；不是通用硬件门槛。

原文位置：SemiAnalysis §14 · [S1]

SECTION 15

Prefill/Midfill 将稀疏路由转成稠密 Expert Batch

Prefill and midfill turn sparse routes into dense expert batches

示例中 128 个新 Token 各选 8 个 Expert，产生 1,024 次路由，分配到 256 Expert 平均每个 4 次。按 Expert 排序可减少重复权重读取，算术强度随每 Expert Token 数 n 增加而提高，直到 Activation/Output/排序开销成为新瓶颈。真实 Router 分布不均匀，不能把平均值当作每个 Expert 的实际负载。

原文位置：SemiAnalysis §15 · [S1]

SECTION 16

Decode 从大 Batch 获益相对有限

Decode gains less from batching

不同请求的 KV 大多私有，Batch 增大并不能像共享 GEMM 权重那样显著降低每请求 KV 扫描字节量；Expert 虽可共享权重，但小 Batch 只激活少数 Expert。作者认为交互式 Decode 的最佳 Batch 可能远小于吞吐导向服务惯用的数百规模，必须按延迟与单位 GPU 产出权衡，而不是宣称 Batch=1 总是最优。

原文位置：SemiAnalysis §16 · [S1]

SECTION 17

调度使分离架构产生规模效益

Scheduling makes disaggregation useful

当 Prefill、Midfill、Decode 各有大规模 Worker 池时，编排器能根据缓存命中、输入长度、SLO 与负载进行匹配；中间 Ready Buffer 解耦确定性较强的 Input Fill 与随机长度的 Decode。分离的优势不是某一对 Worker 天然更快，而是大规模统计复用、避免一种阶段阻塞另一种阶段。

原文位置：SemiAnalysis §17 · [S1]

SECTION 18

反馈可能把小失衡放大成振荡

Feedback can turn a small imbalance into oscillation

若 Prefill Admission 直接受 Decode 请求完成事件驱动，长尾 Decode 会造成 Prefill 降载，随后 Decode 饥饿，再触发 Prefill 突发，系统在满载与空载之间振荡。作者建议 Ready Buffer、平滑 Backlog、分层控制、滞回、为交互流量保留容量，以及不要在系统尚未观测到效果时过快调 Batch。

原文位置：SemiAnalysis §18 · [S1]

SECTION 19

合设与分离架构的取舍

Aggregation Compared to Disaggregation

作者并未把 P/D 分离视为必然最优。对话停顿后，KV 离开 HBM 进入共享存储合理；但一次 Turn 内也可以由一台兼具计算与带宽的 Aggregated Worker 连续完成 Prefill/Midfill/Decode，省去跨 Worker KV 迁移与调度空档。代价是不同阶段必然有部分算力或内存资源闲置；分离方案可为各池配置不同硬件，但增加网络、存储和编排成本。

原文位置：SemiAnalysis §19 · [S1]

SECTION 20

内存带宽与容量是不同优化目标

Memory bandwidth and memory capacity are different objectives

容量首先要覆盖活跃权重、KV、缓冲和安全余量；超出有效需求后，更多 HBM 容量不一定提高每秒可交付 Token。高带宽对交互式推理可能更值钱，闲置 KV 应分层到 DDR/SSD。作者提醒高层堆叠快存还会带来功耗、信号完整性、封装与频率取舍；不能只看 TB/GPU。

原文位置：SemiAnalysis §20 · [S1]

SECTION 21

可复用的模型—硬件映射方法

A practical mapping method

作者给出十步流程：区分四类运行区间；提取重复 Layer Group；测量活跃状态而非总参数；分别选 PP/TP/EP；先映射最大 Attention/KV 操作；固定 Expert 位置；将高频通信保留强 Fabric；在 KV 交叉点停止增加 PP；按阶段差异设计 Batch；把共享存储、调度与 Worker 一起设计。最终不预设单一最优拓扑。

原文位置：SemiAnalysis §21 · [S1]

SECTION 22

下一维度是时间

The next view is time

作者给出单层执行约 50µs—1ms、约 60 层模型对应 15—300 Token/s 的数量级说明；内环 Kernel、路由、归约与同步常需在微秒甚至亚微秒内完成。还要分清时间尺度：本地 Link µs、Token ms、Ready Buffer 0.1—10s、Worker 重配秒到分钟、KV 生命周期分钟到天。交换机的平均带宽不能替代尾延迟和小消息启动成本。

原文位置：SemiAnalysis §22 · [S1]

SECTION 23

案例：Kimi K3 在 Blackwell 上的性能预测

Worked example: projected Kimi K3 performance on Blackwell systems

文章使用自有 Simulator 对 B200、B300、GB200、16—64 GPU 配置进行模型推演，不是实测。8k/32k Decode 在低延迟端常用 PP+TP，而高吞吐/GPU 端倾向简单 Attention Instance 与宽 EP；127k 缓存+1k 追加的 Midfill 对 GB200 的低 TTFT 较有利；8k/32k Prefill 偏计算受限，几种 Blackwell 的模型结果接近。多数所选 Pareto 配置的峰值 HBM 驻留在约 80GB/GPU 以下（仍有 KV 传输缓冲），EP 流量在 Prefill/Midfill 中较集中，Decode 的时间窗平均流量低不代表瞬时突发低。原文这一节内部子标题编号写作 22.1—22.4，属排版编号不一致。

原文位置：SemiAnalysis §23 · [S1]

结语 Closing perspective｜中文转述

作者最终主张：推理系统的正确分析单元不是总参数量，而是“模型的活跃数据流 × 机器的存储/通信/时间层级”。Layer Group 可重复映射，Expert 可独立放置，Attention 受 KV 支配，内环通信应留在强 Fabric，KV 与工作分派通过共享存储和 Scale-out 连接独立 Worker。性能要靠模型、Worker、Rack、存储与调度一起设计。

03｜核心论点与关键数据

项目原文数字/条件应如何解读
运行区间Prefill、Midfill、Decode Attention、Decode Experts不是简单三分法；不同阶段的权重重用、KV 读与 EP 流量差异很大。
Midfill 输入常见追加约 50—5,000 Token，旧上下文可接近百万 Token来自文章所引 AgentX 轨迹与情景描述；不是所有用户的统计分布。
MoE 路由例子128 Token × Top-8 = 1,024 路由；256 Expert，平均 4 路由/Expert排序后可批量 GEMM；平均值不保证负载均匀。
KV 容量基准70kB/Token × 2,000,000 Token ≈ 140GB；双缓冲约 280GB作者的设计示例；加权重与余量得到 400—500GB/Stage，非通用标准。
KV 每 Token 参考新混合 Attention 可能约 25kB/Token；压缩 Attention 参考约 70kB/Token高度依赖层数、KV Head、MLA、精度、稀疏/局部 Attention。
交互时序单层约 50µs—1ms；60 层对应约 15—300 Token/s数量级预算；具体模型、硬件、并行策略会改变。
Kimi K3 模拟B200/B300/GB200；16—64 GPU；8k/32k Prefill、127k+1k Midfill、8k/32k Decode全部是 SemiAnalysis 模拟，不是芯片实测 Benchmark。
模型 Pareto HBM多数最优前沿配置约 <80GB/GPU（含部分实用缓冲估计）特定模型与配置的模拟结果，不意味着大模型只需 80GB HBM。
网络峰值Prefill/Midfill 的 EP 流量更集中；Decode 平均流量低但链路瞬时突发仍高交换机应分别考虑平均利用率、Burst 与尾延迟。

原文定位：§3、§6、§14—16、§22—23，尤其 Figure 19、20、26—29；参见 [S1]。

三个最重要的主张

其一：把推理分成四个数据复用不同的区间，而不是用一个 FLOPS 或 HBM 指标评价所有阶段。其二：强 Scale-up 应围绕每层重复的 Attention/EP 内环布置，Scale-out 更适合较低频、可摊销的 KV 与 Pipeline 传输。其三：容量、带宽、同步、调度构成一个联合约束，增加 GPU 数量或 HBM 容量不一定带来相同比例的有效 Token 产出。

Scale-out / Storage 外环
KV Blob、Pipeline Stage Activation、调度控制、冷热数据分层。关注吞吐、流完成时间、NIC 带宽、KV 热点、缓存命中与队列稳定性。

这是根据原文机制归纳的逻辑拓扑，不是某个产品的已验证物理布线。NVIDIA Dynamo 官方文档确认 P/D 分离可用 NIXL 直接传 GPU KV；Mooncake 官方实现则提供分布式 KV Store 和 Transfer Engine，证明“共享 KV + Worker 解耦”有实际软件实现。[S3][S4]

4.2 一个可核算的 EP 网络流量下界模型

独立推断对一个 Token 在 LMoE 个 MoE 层中依次选择 k 个远端 Expert、隐藏维度 d、Activation 每元素 s 字节的场景，若 Dispatch 与 Combine 均需跨域搬运完整 Activation，逻辑传输字节量近似：

B_EP/token ≈ 2 × L_MoE × k × d × s × p_remote

其中 p_remote 表示路由消息中实际跨目标网络边界的比例；系数 2 表示发送 Activation 与返回 Expert Output。此式未计 Header、量化、重传、组播/复制、拓扑 Hop 放大、融合算子和跨 GPU 本地化，因此不是链路端口的直接实测值。

以 DeepSeek-V3 官方配置作为独立示例：d=7168、k=8、总层数 61、Dense 层 3，若剩余 58 层均参与远端 EP、BF16 2B、p_remote=1，则约 13.3 MB / 输出 Token（十进制），100 Token/s 对应约 1.33 GB/s 的所有逻辑 EP 消息字节率。实际网络端口的峰值与平均值还取决于 Rank 分布、Layer 并行、路由分桶与 Hop；此计算不是 SemiAnalysis 的实测或 DeepSeek 部署带宽。[S6]

单个 BF16 Activation 约 14.3KB，Top-8 产生多个目的地；因此即使长期平均字节率不高，仍会有每层重复的 Fan-out、同步和 Burst。对 100T Scale-up Switch 而言，报文分布、拥塞热点、目的端队列、尾延迟与总吞吐一样重要。

4.3 为什么 Prefill/Midfill 能把 Expert GEMM 做大？

128 Token × Top-8 产生 1,024 次 Expert 访问；若 256 个 Expert 且理想均匀分布，平均每个 Expert 得到 4 个 Token。一个粗略的占用估计为 256 × (1 − (1 − 1/256)1024) ≈ 251 个 Expert 被访问。此估计假设各次选择独立均匀，真实 Router 的负载均衡、Top-k 去重和热点会改变结果。排序/分桶把多个 Token 送给同一个 Expert，从而摊薄 HBM 权重读取；Decode 小 Batch 下这种共享概率大幅下降。

独立校验原文 §15 的算术强度表达式可作方向性解释，但真实 Activation 与 Output 字节量通常随 n 增加，严谨建模应使用 AI ≈ FLOPs(n) / [weight_bytes + n×(input_bytes+output_bytes) + routing_bytes]，并根据具体 Expert GEMM 和缓存复用核算。不能把简化式当作精确硬件性能模型。

4.4 KV 迁移：容量、带宽与完成时间要分别计算

原文的 70kB/Token × 2M Token ≈ 140GB 是某个 Stage 的容量规划示例。对于单次 KV 迁移，传输量应以该请求的实际层数、上下文长度、KV 压缩与分片方式重新计算。示例：若 500k Token × 70kB/Token = 35GB，单条理想 800Gb/s 链路理论上限约 100GB/s，不计任何开销的最低序列化时间为 0.35s；400Gb/s 约 0.7s。实际还受 NIC 数、PCIe、GPU Direct、内存读写、拥塞和并发影响。

T_KV ≥ KV_bytes / B_effective
总完成时间 ≈ 准备/注册 + 排队 + 网络传输 + 目标可用性同步

若 Prefill 与 Decode 在同一 Worker 内连续运行，可省去这一迁移，但可能损失专用资源配置的效率；因此不能单凭 KV 大小决定 P/D 分离一定好或坏。NVIDIA Dynamo 官方文档说明 NIXL 支持非阻塞 KV 传输与 KV-aware Routing。[S3]

4.5 PP 深度为何存在“KV 交叉点”

M_stage ≈ W/P + M_KV,stage + M_working + M_slack

增加 PP 深度 P 会分摊权重 W，但满流水需要多个同时活跃的请求，各 Stage 的 KV 活跃集合可能随流水并发数增加，无法按 1/P 等比例缩减。Stage 切换与 Pipeline Bubble 也会上升。正确设计方法是先确定目标 Context/Batch/SLO，再计算 Weight/KV/Buffer 与故障余量，而不是单纯为了让单卡权重更小而不断扩 PP。

4.6 HBM、DRAM、SSD 与 Chiplet/封装

独立推断对于交互式 Decode，HBM 带宽与低延迟更可能决定 Token 产出；HBM 容量只需覆盖活跃工作集与安全余量。共享 CPU DRAM、内存池和 SSD 可降低长会话空闲 KV 的 HBM 占用，但增加跨层传输与缓存管理复杂度。更高密度 3D DRAM、Hybrid Bonding 或 SRAM-heavy Expert 引擎可改变容量/带宽/能耗边界，却同时增加散热、供电、封装良率与网络扇出问题。原文关于新型存储的论述包含前瞻性判断，不是已验证的量产路线。

06｜值得验证的问题与一手来源

Q1｜EP 真正需要多大的 Scale-up Domain？

固定模型与 Batch，扫描 EP8/16/32/64/128、Expert 放置、Rank 到 Rack 映射；分别测 Dispatch/Combine 字节、Burst、P99、同步等待与吞吐。若跨域 EP 后小消息启动或尾延迟主导，扩大 Domain 的收益才有依据。

Q2｜Midfill 是否值得独立 Worker 池？

按旧 KV 长度、新 Token 数、缓存命中与 SLO 分桶，比较合设/分离的 TTFT、TPOT、GPU 利用率与 KV 搬运成本；观察长 Midfill 是否干扰 Decode。

Q3｜400—500GB/Stage 的边界条件是什么？

将 MLA/GQA/Hybrid Attention、并发请求数、KV 精度、双缓冲、碎片和故障冗余纳入容量模型，比较“加 PP”与“加快存/带宽”的边际收益。

Q4｜共享 KV 的数据面能否闭合？

量测 NIXL、Mooncake Store 的 KV 对象大小分布、源/目的 GPU Direct 能力、RDMA 分片、缓存重建、跨节点复制、尾延迟和热 Key 放大。

Q5｜是否真的能把 EP 与 KV 分离到两类 Fabric？

根据模型执行轨迹核对每层 All-to-All 的链路频率和跨 Worker KV 的迁移频率；在物理拓扑上验证 NIC、Switch、HBM 的共享争用，不能只按“Scale-up/Scale-out”名称划线。

Q6｜预测模型与真实产品差多少？

对 Kimi K3 或公开可复现 MoE 模型，在 B200/B300/GB200 上采集 TTFT/TPOT、J/token、HBM Residency、NVLink Burst、EP Rank Map，和 Figure 26—29 的趋势逐项对照。若没有模拟器配置，不应引用图上未公开的精确数值。
