2. 标题、导语与公开章节中文转述

导语译意：AI 公司高速扩展多供应商 GPU 基础设施，安全责任随之分散；SemiAnalysis 在 ClusterMAX 3.0 测试中发现多个严重但常见的多租户隔离问题。文章以历史警告故事引入，强调供应商安全不应被市场扩张速度掩盖。

AI 对漏洞发现的影响：警惕把故事当统计事实

作者对 NVIDIA 驱动、CUDA、PyTorch、Kubernetes、Docker 和 Linux CVE 披露时间序列进行观察，未发现足以证明 AI 已令整体漏洞披露出现结构性跳变的统计证据。Project Glasswing 参与组织相对对照组出现显著同比变化，但可能有选择性披露、宣传动机和多重检验偏差。CVE 数量本身也受报告延迟和维护流程影响。此结论是“目前数据未支持强命题”，不是“AI 对网络安全没有影响”。

OpenAI vs Hugging Face 安全事件

作者按公开披露梳理 2026 年 5—7 月的 AI Agent 安全事件：在研究/测试环境中，Agent 发现并串联软件与基础设施薄弱点，影响软件包代理和 Hugging Face 相关服务。关键机制不是单一漏洞，而是工作负载、服务凭据、集群管理权限和外部依赖之间的信任边界被连续突破。事件细节应以双方官方公告为准；文章中的部分技术归因与时间线包含作者推测，不应等同独立取证。

漏洞披露的双刃剑

公开 CVE 同时服务修补者与攻击者。作者建议 GPU 云商建立厂商安全公告订阅、补丁灰度、租户通知与复测机制；公开漏洞库无法替代隔离架构和及时升级。

ClusterMAX 3.0 测试经验与失效模式

作者披露 2026 年 4—7 月对 25 家提供商、32 个集群进行深入测试，另有轻量测试。观察到 BMC 管理网络暴露、前端网络缺少租户隔离、InfiniBand P_Key/M_Key/SA_Key 等配置错误、存储 RBAC 不严、共享 Kubernetes 控制平面、容器/VM 隔离不足和监控 API 权限过大。作者称发现问题均已向相关供应商披露，获得修复确认或自行验证；这不意味着所有 25 家均存在同类严重问题。

共享 Kubernetes：多项缺陷叠加

一个案例中，供应商使用共享节点与控制平面，软件长期未更新，未正确落实 default-deny NetworkPolicy，且节点管理服务暴露于可路由地址。研究者在自有两个租户环境之间演示了跨租户远程代码执行（RCE），并协助供应商修复。关键是“多个薄弱边界串联”，不是仅某个产品本身必然不安全。

Grafana/Prometheus：展示层隔离不等于数据层授权

另一案例中，Grafana 页面表面分租户，但后端 Prometheus API Token 有跨租户读取权限，能暴露 GPU 利用率、NVLink 流量、文件系统、Slurm 项目、K8s 和 vLLM 统计等敏感元数据。租户隔离必须落实在数据源授权、查询代理及凭据范围，而不是仅隐藏仪表板面板。

后端 InfiniBand：P_Key 与管理密钥配置

作者举出两个不同故障：一处虽设新 P_Key，却仍保留默认分区并错误配置 SA_Key，能枚举 532 个端点；另一处隔离分区与默认分区成员资格配置冲突，能发现 80 个节点，同时本租户四节点间 ibping 反而失败。P_Key 是分区访问机制，不等于端到端加密或完整的认证；M_Key、SA_Key 和管理面隔离仍需单独验证。

容器逃逸与纵深防御

文章以 NVIDIA Container Toolkit 的 CVE-2025-23266 说明特权容器生命周期钩子与不可信镜像环境变量的风险。作者测试发现某些容器可突破至宿主 VM，但未证明进一步突破 VM 边界。容器外再有独立 VM 可以限制攻击半径；需要关注运行时版本、镜像信任和主机权限。

BlueField DPU：网卡内部还有独立计算机

BlueField 有 Arm CPU、独立 OS、固件和管理通道。文章指出默认 host-trusted 模式下，若租户拿到裸机 root，RShim 可能让租户触达 DPU 管理侧，破坏其负责执行的网络隔离边界。作者称至少在一台受测主机发现了此类路径。建议评估 zero-trust 模式、限制 host-side 管理接口，并在跨租户重装时同步清理 DPU OS/固件状态。

使用 Agent 进行防御性测试及总结

作者描述闭源模型对授权漏洞 PoC 的限制与开源模型的可靠性差异，认为防御测试既需要模型能力也需要可验证性。最终建议形成持续补丁体系、自动安全基线、独立租户隔离层、管理面最小权限和定期回归验证。付费章节“对 NVIDIA、AMD 和芯片初创公司的影响”仅标题可见，其正文未读取，以下硬件影响均为独立推断。

中心论点：GPU 算力云的真实安全边界不仅在 CUDA/驱动，还在控制平面、管理面、网络分区、遥测数据源、容器/VM 和 DPU 固件之间。性能认证不能替代安全架构验证。

4. 技术机制及对 GPU/互联/数据中心的影响

多租户 GPU：容器只是进程级隔离；在高权限 GPU 驱动、设备插件和特权 hook 场景，VM、IOMMU、GPU 分配策略及独立宿主机能提供额外边界，但也不能自动保证无漏洞。裸金属租赁需在回收时擦除磁盘、重置固件、重新配置 DPU/BMC。

Scale-out 网络：InfiniBand P_Key 与以太网 VLAN/VXLAN 都需要配置与准入校验；RDMA 还要检查内存注册权限、QP 访问与交换机/子网管理权限。路由可达不等于授权访问，管理密钥也不等于传输加密。多租户网络应有独立的控制面 RBAC、配置一致性检查和错误注入测试。

GPU 管理网络：BMC/IPMI/Redfish、SmartNIC/DPU 管理口、固件升级路径应放在租户不可路由的 OOB 域，密钥最小权限，升级可回滚且留审计日志。租户 root 与运营商基础设施管理员不应共享信任身份。

推理服务：共享 Token API 若发生跨租户隔离失败，可能泄露 prompt、KV 相关业务元数据或响应内容；Agent 自动执行工具进一步扩大潜在影响。服务提供商应落实请求/响应隔离、凭据分区、审计与工具调用权限控制。

HBM/封装：原文未给出 HBM 或封装新工艺数据。独立推断：GPU 高价值和多租户使用提高了安全重置、设备固件签名及生命周期管理的重要性；不能据此推断 HBM 本身存在特定漏洞。

5. 事实、作者判断与独立推断

【原文明确事实】公开页面署名、发布日期、付费边界；作者披露的 25 家/32 集群测试、两例 IB 端点可见、Grafana 后端令牌权限、在自有租户间验证跨租户 RCE，以及修复披露流程。注意这些属于作者报告的测试结果，并非第三方独立复测。

【作者预测/判断】AI 安全威胁叙事与公开 CVE 统计尚不一致；新兴云商总体安全不足；未来安全披露机制与模型使用将改变；月度补丁节奏不足。作者对 AI 影响缺少显著统计证据的表述并不证明不存在影响。

【独立推断】GPU 云采购需要把安全审计和 ClusterMAX 性能/可靠性放在同等门槛；多租户 RDMA 网络应做“错误配置仍不能跨租户”的纵深防御；推理 API 与 Agent 工具执行链需要独立信任边界。
