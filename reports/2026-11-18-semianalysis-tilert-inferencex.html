2. 原文翻译与按原文结构中文转述

导语中文转述：用户愿意为更低延迟的“快速模式”付费，实时语音和互动助手对逐 token 延迟特别敏感。GPU 擅长大批量吞吐，却不一定擅长 batch=1 的亚毫秒级 TPOT。文章以 HGX B200 的理论 HBM 带宽为例，说明实际输出速度与带宽上界相距甚远，问题转向 kernel launch、同步、内存访问延迟及中间结果写回。TileRT 将整个 Decode 计算图预编译成持久驻留的 GPU Engine Kernel，以减少传统多内核边界的开销。

InferenceX｜推理基准平台

InferenceX 是作者团队持续更新的开放基准，研究延迟—吞吐量帕累托边界。不能把不同精度、不同模型版本、不同硬件规模、不同 MTP 配置的点当作严格 A/B 实验；下述数值均为文章披露的特定测试点。

Throughput vs Interactivity Curve｜吞吐与交互性曲线

交互性（tok/s/user）衡量单用户输出速度，对应 TPOT 的倒数；吞吐量（tok/s/GPU）衡量单位 GPU 汇总处理量，影响每 token 成本。提高 batch 可以摊薄权重读取和调度开销，但每用户速度通常下降。文章展示一组配置中从约25到260 tok/s/user 的交互性提升，伴随每 GPU 吞吐从约5900下降至200 tok/s/GPU；这是同图点位对比，不能泛化为所有模型。

TileRT results｜实测结果

在8k输入/1k输出的 GLM-5 系列测试中，8卡 B200 的 TileRT FP8 达到340 tok/s/user；此前数据集的 GB300 NVL72 NVFP4+MTP 最快为181.4，B300 FP8+MTP 为113.6。1k/1k 场景 TileRT FP8 为494.2 tok/s/user，对照最快传统 FP4 为256.3，传统 FP8 为136.3。不同精度、硬件、推测解码和模型配置限制了因果归因。

在8k/1k、并发12的传统 GB300 FP4+MTP 点位，约154 tok/s/user 且约240总tok/s/GPU；TileRT 为340 tok/s/user 但仅160.4总tok/s/GPU。文章强调其发布时一个 Decode 节点仅允许一个在途请求：这是针对极低延迟的服务档位，而非全面吞吐替代。Decode 尾段耗时约3.01秒，对照 NVFP4+MTP 6.54秒、MI355X 18.18秒；TTFT 并非其主要优势。

But What Exactly is TileRT?｜TileRT 的执行机制

传统引擎运行大量离散 CUDA kernel，launch/sync 与 HBM 中间结果写回在小 batch 下无法摊薄。CUDA Graph 将 kernel 启动图录制后重放，但每个 kernel 仍是独立执行边界；TileRT 则将 Decode 图 AoT 静态展开为持续运行的单个 Engine Kernel。其内部按 tile 拆分任务，使用 warp/block specialization 重叠异步访存、矩阵计算、通信，尽量让中间值留在寄存器、共享内存或 L2，减少全局内存往返。

在 GLM-5.1 Attention 的特定实现中，GPU0 作为 Sparse Indexer 执行 Top-K、稀疏索引和路由，GPU1–7 负责 MLA、GEMM、稀疏 Attention 和 AllReduce。这里是异构 GPU 角色分工，并非所有 GPU 必须执行同一份算子。Collective 和同步融合进 tile 级流水，目标是把串行计算—同步—计算改成通信计算重叠。

PD Disaggregated Engine with vLLM <> TileRT｜分离式 Prefill/Decode

vLLM 保留 Prefill、Scheduler、Chunked Prefill、Prefix Cache、OpenAI API 等通用能力，TileRT 专做极低延迟 Decode。共享 Prefill Pool 可连接普通 vLLM Decode Pool 和 TileRT Decode Pool；路由器将高速请求标记给 TileRTConnector，其他请求由原生 Connector 处理。通过 vLLM MultiConnector API 与 Mooncake/NIXL 搬运 KV Cache；TileRT v0.1.5 每节点一条在途请求，Router 需限流及背压。

How does TileRT compare to Cerebras/Groq/SambaNova?｜专用芯片对比

Groq 的确定性编译执行与片上 SRAM、Cerebras 晶圆级空间映射、SambaNova 可重构数据流架构，都通过减少执行边界、调度和存储往返优化低延迟。TileRT 以软件方式将部分数据流思想映射到 SIMT GPU，但无法消除 GPU 固有硬件调度、HBM 延迟和模型容量限制。作者认为 GPU 可灵活将通用集群部分容量切换为高价高速 Decode 档位；专用芯片在极端性能与 SRAM roofline 上仍可能占优，但采购后 Prefill/Decode 比例较难快速调整。

Why Is TileRT Development Slow?｜为何开发缓慢

静态展开带来模型专用性：Attention、稀疏路由、Tile Shape、Pipeline Depth、寄存器/Shared Memory/L2 分配、GPU 角色都需要重新调优。文章当时主要支持 GLM-5/5.1 和 DeepSeek-V3.2；MiMo V2.5 Pro UltraSpeed 是联合优化但尚未开源。TileOPs 试图用机器可读的算子描述驱动代码生成、测试和 roofline 对比；单体持久内核也使常规逐 kernel Profiler 的反馈变困难。

Next steps with TileRT <> InferenceX｜后续测试

计划使用 AgentX 真实多轮编码 Agent Trace 检验长上下文、多轮增量 KV 传输、Prefix Cache、Offload 和路由；文章披露输入长度中位数约140k token、理论缓存命中率上限中位数99.2%，但该上限不是实际命中率。还计划测 batch=2/4/8，以寻找低延迟收益与总吞吐的转折点。

4. 对 AI 算力硬件、HBM、互联和推理架构的影响

GPU 微架构：算力峰值和 HBM TB/s 不能独立预测 TPOT。小 batch 下应建立 kernel 边界、global sync、L2/Shared Memory 复用、CTA 驻留和实际 memory latency 的联合模型。Persistent Kernel 可能增加寄存器压力、降低 occupancy，编译时间和模型兼容性也属于系统成本。

HBM：文章64TB/s÷21GB/token≈3047 tok/s/user 是极简带宽 roofline；真实推理还包含 KV Cache、Attention、AllReduce、权重分片、访存效率及跨 GPU 数据交换。不能由此得出 HBM 带宽已经不重要。TileRT 优化中间数据流量，但模型参数和 KV 容量仍受 HBM 限制。

Scale-up 网络：GPU0 专职 Sparse Indexer、其余 GPU 做 MLA/GEMM 的异构角色会改变广播、索引传输与 AllReduce 的时序。对 NVLink/UALink 设计，更重要的是短消息启动延迟、Collective 同步尾延迟、通信与计算 overlap，而非仅宣称聚合带宽。原文没有给出可直接作为交换芯片 PRD 的网络 p99 时延或消息尺寸。

Scale-out 与 KV Transfer：Prefill/Decode 解耦引入 KV Cache 迁移，Mooncake/NIXL 网络路径、NIC/RDMA、增量 KV 传输、Prefix Cache 命中和背压会决定端到端收益。若每轮都搬运全量140k上下文，Decode 提速可能被传输抵消；需按每轮新增 token、KV bytes/token、命中率和网络有效吞吐建立容量模型。

部署与商业：将普通 vLLM Decode 和 TileRT 极速 Decode 分成两类服务档位，可在现有 GPU 集群动态调配硬件；但当高交互需求扩大，batch=1 的节点利用率和排队时延可能使成本恶化。比较专用推理芯片应使用同模型、同精度、同SLO、同端到端网络与同成本口径。

5. 事实、作者判断、独立推断与反例

【原文明确事实（披露而非全部独立复测）】文章给出 B200/GB300/B300 的特定 InferenceX 测试点；说明 TileRT persistent Engine Kernel、GPU角色专用化、vLLM MultiConnector、Mooncake/NIXL 的组合；发布时 Decode 节点仅支持一条在途请求；公开正文在 TCO 深入部分进入付费墙。

【作者预测/判断】高交互极速档位会形成较高毛利市场；GPU 软件模拟数据流执行可能压缩 Cerebras/Groq/SambaNova 的部分可服务市场；通用 GPU 资源可重分配性具有商业优势；同成本交互性最高约1.9倍的经济性属于作者公开概述，付费细节未核验。

【独立推断】高交互推理对交换芯片 PRD 的要求可能从单纯带宽转向 p99 集合通信时延、同步抖动与 KV 迁移 QoS；高吞吐 Prefill 池和极速 Decode 池宜独立配置资源配额、拥塞控制和故障域。

【反例/边界】若 batch上升或模型频繁变更，TileRT 的 AoT 编译和batch=1限制可能使其整体TCO落后传统引擎；若网络 KV 迁移耗时超过节约的 Decode 时间，端到端收益消失；在极端小模型/片上 SRAM 命中率高的场景，专用数据流芯片仍可能领先。
