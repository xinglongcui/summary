二、原文翻译与中文转述（按公开结构）

标题翻译：Engram 嵌入机制：面向高效 DRAM/SSD 卸载的软硬件协同设计。副标题翻译：新模型架构如何改变 DRAM/NVMe 的市场空间，以及 DeepSeek V4.1 Flash、AgentX、InferenceX 与 NVMe 实验。作者：Bryan Shan 等六人；日期：2026 年 9 月 18 日。

2.1 导语（公开）

文章从 Transformer 的两类能力切入：一类是 Attention/MoE 的动态计算，另一类是可以通过确定性索引取得的局部词组模式。Engram 在常规 Token Embedding 之外加入可学习的多 Token 查表；重复出现的局部模式可以直接取得表项向量，减少在前几层通过 Attention/FFN 反复重建这类模式的需求。作者将其视为“计算与记忆分工”的模型架构变化，而非单纯缓存优化。

作者强调 Engram 的访问地址由 Token ID 决定，而非等待当前层 Hidden State 计算完才知道，因此可以在前序 Transformer 层计算时提前从 Host DRAM 拉取表项。大表不必完整占用 HBM，HBM 可留给其他模型权重、KV Cache 和更高并发。进一步使用 NVMe 是第二级容量扩展思路，但作者明确指出 SSD 方案需要实际服务成本验证。

作者使用约 189 GiB 的 DeepSeek V4.1 Flash Engram 配置进行 mmap/SSD 实验；同时借助 InferenceX 的 AgentX 服务测试比较 NVIDIA 与 AMD 平台。文中对 GPU 厂商性能的评论属于该测试时点的作者判断，不能脱离模型版本、软件镜像、成本口径推广到全部负载。

关键短句①：“Engram’s table is large, but each lookup is small.”
译文：Engram 表很大，但每次查表的数据量很小。

2.2 Engram Benefits｜Engram 的收益（公开）

DeepSeek 未发布原论文中两套训练完成的 Engram 模型权重。SemiAnalysis 团队因此使用公开代码和超参数，在 FineWeb-Edu 上复现实验，每次训练约 6×10¹⁸ FLOPs（作者估算），观察到类似的 U 型稀疏容量分配趋势：将全部稀疏参数预算都交给 MoE 并非总是最佳，部分容量分给 Engram 后，模型质量可以改善。作者还观察到加入 Engram 后，前层表示与更深层的相似性发生变化，与“减少早层静态模式重建”的机制相符。

核验边界：这是作者独立的小规模复现实验，不是 DeepSeek 原论文中的 27B 实验；两组 FLOPs、数据集与模型不能混为一谈。DeepSeek 原论文的同参数、同 FLOPs 对照与 U 型曲线见 论文 §3、Figure 3。

2.3 What is Being Memorized?｜Engram 实际记住什么？（公开）

作者扫描模型的 Gate Score，发现强响应的 N-gram 包括人名、代码片段、关系表达和网页/文档模板；其中也有看似无意义但频繁重复的许可声明、参考文献和 API 样板。它们可能是训练目标下的高性价比预测捷径，不代表系统按人类判断存储“重要知识”。

作者特别澄清：展示的案例偏向有趣，并非按 Gate 强度进行无偏抽样；也无法从评估语料扫描推断训练暴露频率或各类别占用了多少表容量。高 Gate 不等于缓存热行：Gate 需要取回表项后才能计算；若想跳过低价值查表，需要一个在取表前就能运行的额外预测器，而不是直接利用现有 Gate。

2.4 Removing Engram｜移除 Engram 的消融实验（公开）

原始 DeepSeek 论文的“训练后推理阶段移除 Engram”实验显示，部分事实知识任务仅保留原性能的 29%–44%，阅读理解任务则保留 81%–93%。这反映的是同一个已经依赖 Engram 训练的模型在推理时突然失去该模块后的分布失配；不能拿来当作“有 Engram 训练模型与从未使用 Engram 训练模型”的公平性能差距。

SemiAnalysis 自己的消融还发现：禁用 Engram 会使多个语料域的 Token 似然恶化，百科文本和部分代码语料尤其明显；但 GSM8K 准确率变化处于实验波动范围内。作者使用 CRUXEval 的 Teacher-forced 参考答案实验，发现保留 Engram 时 Loss 为 0.2848 bits/token；移除 Engram 后升至 0.3093；若再强制使用原来 Engram-on 的 Expert 选择，进一步恶化至 0.3375。说明缺少记忆后，MoE 重新路由在一定程度上起到了补偿作用。

在同一 CRUXEval 设置中，作者分别禁用 Prefill、Decode 或两阶段 Engram，观察到正确率下降、生成 Token 增加；仅在 Prefill 保留 Engram 通常优于仅在 Decode 保留。作者推测原因是 Prefill 生成了语义更丰富的 KV Cache，使 Decode 即使缺少 Engram 也能部分受益。这一解释是机制假说，不是独立测量了 KV 信息量。

2.5 Agentic Inference Serving Performance｜Agent 场景推理服务性能（公开）

作者的 V4.1 Flash 配置在两层 Engram 中，每层对每个 Token 位置请求 24 行，合计约 12.4 KiB/Token 位置；在四 GPU 切分配置下，平均每 GPU 约 3.1 KiB。作者同时展示不同 NVIDIA GPU 和 MI355X 的 AgentX/InferenceX 结果，并称发布初期 AMD 的 ROCm/vLLM 镜像适配落后，特定成本口径下 MI355X 的性能/美元较 B200 差约 2–4 倍。

限定：文中还出现最高 14.8×、42× 的极端相对值，属于不同对照点的“up to”结果；不可将它们当作跨模型、跨日期、跨软件栈的固定性能倍率。该页面图表依赖动态交互，本次可核查文章中的描述与 InferenceX 公开入口，未独立复算其所有原始测量点。

2.6 AgentX Engram DRAM Offloading Improving Performance｜DRAM 卸载如何改善 AgentX（公开）

作者对比两条路径：HBM 表直接从 GPU 显存读取；DRAM 卸载则使用 UVA（Unified Virtual Addressing），GPU Kernel 直接从锁页的主机内存读取表项，并在 GPU 上完成行选择与反量化。两种路径使用相同的 GPU Kernel，且都支持完整 Decode Graph；DRAM 方案的优化重点是异步访问与计算重叠。

在作者的 B300 测试中，Engram 不占用 HBM 后，部分配置可以从 TP4 缩减到 TP2，使性能—成本 Pareto 曲线改善最高约 1.6×。这不只是“DRAM 比 HBM 更快”，而是释放 HBM 容量后可以减少每个 Replica 所需的 GPU 数量，同时降低 TP 通信和系统成本。作者称将 Engram 放回 HBM 并未带来超出运行波动的改善；这一结果限于所述 week-0 软件栈及负载。

文章由此主张，在部分推理场景中 HBM 带宽的经济价值高于 HBM 容量，并进一步讨论 4-hi HBM 的每美元带宽。但这属于依赖工作负载与成本模型的观点；不能推断所有 LLM 都不再需要大容量 HBM，更不能将文中“0Hi HBM”式设想视为已验证路线图。

2.7 SSD Offloading｜SSD 卸载实验（公开）

作者在 B200 上构建了未优化的 vLLM 分支，使用本地 SSD 上的 mmap 文件保存 Engram 表，并明确表示当时未能启用 GDS。与 UVA 直接从锁页 DRAM 读取不同，SSD 路径需要将 Row ID 传给 CPU、去重、将对应表项收集到 Pinned Buffer、再传回 GPU 反量化；这些步骤位于 GPU Graph 的不同执行片段之间，产生额外调度和传输开销。

即使文件页已经处于 OS Page Cache 中、不再产生物理 SSD 读取，CPU 协调、Gather、拷贝等开销仍然存在，因此“暖缓存的 SSD 文件”也可能慢于直接 UVA 的 DRAM 表。文章在所测 B200 配置中观察到：DRAM 在吞吐/成本和 P90 交互速度两项指标上都支配 SSD 曲线；接近 125 tokens/s/user 时，作者报告的数值为 121 million 对 52 million（其图表所述 Token/$ 指标），比例约 2.33×。该绝对量纲很不寻常，未获得原始指标定义与数据导出，不宜把 121 million tokens/$ 当作通用成本常数。

作者指出，SSD 价格更低并不自动意味着服务成本更低：如果仍需相同四颗昂贵 GPU、相同服务器，释放主机 DRAM 容量却没有改变服务器配置或可承载的有效工作量，那么额外的 SSD 路径成本无法得到补偿。结论仅覆盖这套未优化的 SSD 实现与实测点，不是对未来 GDS/CXL/SSD 层级方案的普遍否定。

关键短句②：“Cheaper storage does not automatically produce a cheaper inference service.”
译文：存储介质更便宜，并不自动意味着推理服务更便宜。

四、技术机制与对 AI 硬件、HBM、网络、推理架构的影响

4.1 Engram 为什么可以提前读？与 MoE 的关键区别

DeepSeek 的 Engram 先将 Token ID 归一化，再构造局部 N-gram，使用多个 Hash Head 将其映射到嵌入表索引。检索到的静态向量再与当前 Hidden State 通过 Context-aware Gate 融合，并经轻量卷积/残差接入模型。索引依赖 Token 序列，不依赖当前层 Hidden State，因此即使 Gate 尚未算出，也能预先发起表项读取。

相比之下，MoE Expert 的路由通常需要当前层 Hidden State 经过 Router 才能确定目标 Expert；其 Dispatch/Combine 通信不能在模型尚未生成相应 Hidden State 时完全确定。Engram 的“可提前寻址”因此使 Host DRAM 的访问延迟更容易隐藏。

Token IDs → N-gram / Hash → Engram Row IDs → 异步 Prefetch（Host DRAM）
前序 Transformer Layers 计算 ↗ 与预取重叠
→ Engram Gate + Fusion → Attention / MoE → 后续层

需要注意：可预测地址不等于读取一定命中缓存，也不等于 PCIe 延迟为零。若预取晚于使用时刻，GPU 仍会停顿。模型需要在“早插入更有利于表示学习”和“晚插入能提供更长预取窗口”之间做协同设计。见 原论文 §2.5、Figure 2。

4.2 HBM → Host DRAM：容量释放为何可能胜过访问速度

对于容量巨大的稀疏表，总参数量并不等于每 Token 读取量。例如作者的 189 GiB 表，每 Token 位置只请求约 12.4 KiB。若每个 Replica 只需随机取少量行，将表完整常驻 HBM 的收益可能很小，但会显著挤占模型权重和 KV Cache 空间。

HBM 容量释放可触发离散的系统配置变化：TP4 才能装下的 Replica 可能缩到 TP2。这样减少每个请求涉及的 GPU 数量、TP Collective 与跨卡通信，并可能让同一 GPU 池部署更多 Replica。1.6× 改善是端到端系统配置收益，而非 DRAM 访问带宽高于 HBM。

需要测量的不是单一 GPU Memory Bandwidth，而是 HBM 实际占用、PCIe/Host DRAM 随机读取尾延迟、UVA 读事务、Pinned Memory 开销、NUMA 距离、Page Fault、Graph 执行稳定性与服务端 P90/P99。

4.3 一个简单流量下界：小数据量不等于低延迟要求

D_Engram ≈ 12.4 KiB × N_token_positions
R_Engram ≈ 12.4 KiB × token_positions/s（单 Replica 全模型）
例如 10,000 token positions/s ≈ 121 MiB/s；100,000 ≈ 1.18 GiB/s。

这是根据作者配置计算的纯表项 Payload 量级，不是实测 PCIe 流量。真实传输还受事务粒度、重复行、缓存命中、并发、读放大、索引/控制消息影响。Prefill 可能同时为大量 Token 位置预取，而 Decode 每步每序列产生新位置，二者对并发与尾延迟的压力不同。即使平均带宽很低，分散的随机读取仍可能导致关键路径停顿。

4.4 为什么 mmap + SSD 在作者实验中没有赢

作者的 SSD 路径不是“GPU 直接从 SSD 获取已知行”，而是 SSD/mmap → OS Page Cache / CPU Gather → Pinned Buffer → GPU Copy → Dequantize。其中 mmap 是文件映射机制，并不保证每次访问真的触及 SSD；暖缓存时可能完全由 DRAM 提供数据，但 CPU 协调与拷贝仍在。

与之相比，DRAM/UVA 路径是 GPU Kernel → Pinned Host DRAM → GPU 内部选择/反量化。SSD 路径增加了 CPU 往返和 GPU Graph 分段，因而即使介质成本更低，端到端 TPOT 和 Token/$ 也可能更差。作者未启用 GDS，无法从这一实验推断“经过充分优化的 GPU Direct Storage 仍然一定不划算”。

对 HBM 的判断：模型通过稀疏查表确实可能降低部分权重的 HBM 容量需求，但 Attention KV、激活、Dense/MoE 权重和计算吞吐依然要求高带宽存储。4-hi HBM 的成本优势需要与具体 SKU、堆叠数量、容量门槛和带宽需求共同测算；“HBM 容量不重要”不是已证事实。

4.6 对超节点和 P/D 分离推理的潜在影响

如果 Engram 仅在 Prefill 执行，而 Decode 使用其影响后的 KV Cache，可能在不明显损失质量的条件下减少 Decode 端随机查表。但 SemiAnalysis 只在特定 CRUXEval 消融中观察到相关现象，不能直接推出可用的生产优化策略。需要对不同模型、上下文长度和任务测量正确率、TPOT 与 KV Transfer 成本。

在 EP 较大的 MoE 超节点中，Engram 的确定性表访问可以与前层计算重叠，而 MoE 的 Dispatch/Combine 仍需要 Scale-up Fabric；如果释放 HBM 后减少 TP Degree，系统的主要变化可能是每个 Replica 的计算—通信拓扑，而非交换机物理带宽需求同比下降。需要用端到端 Trace 区分两者。

六、值得验证的问题与一手来源

6.1 必须补的实验

  • 端到端阶段拆解：将 Engram Prefetch、UVA 读取、Gate/Dequantize、MoE Dispatch/Combine、KV Cache 访问映射到同一 GPU/CPU/PCIe 时间线，测量平均与 P99。
  • 固定 GPU 预算的 TP 对照：比较 HBM-TP4、DRAM-TP4、DRAM-TP2，在相同模型质量、输入/输出长度、并发与 SLA 下计算总 Token/$、GPU 利用率和 Replica 数。
  • 真实缓存热度：测量 Row ID 的访问频率、Zipf 参数、重用距离、HBM/DRAM/SSD 分层命中率；不能用 Gate 强度代替访问热度。
  • SSD 优化上限：分别测试 mmap 冷/暖缓存、CPU Gather、GDS 可用路径、Batch Gather、异步 I/O 和多级缓存，报告真实 SSD 读量与 CPU 利用率。
  • Host 侧瓶颈：测量 PCIe 读延迟、NUMA 拓扑、Pinned Memory 规模、主机 DRAM 带宽及多 Replica 并发争用。
  • P/D 分离：检验“Prefill 保留 Engram、Decode 降低访问”对质量、KV Transfer、P90 TPOT 的影响，区分单任务消融与生产可用性。
  • 成本口径：核对文章 121m/52m Token/$ 图表的具体定义、计价周期、GPU 租价、服务器 DRAM/SSD 成本和总拥有成本；避免将绝对数字误用。
