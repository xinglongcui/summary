为什么 4-hi HBM 可能比 8-hi / 12-hi 更适合推理？

核心结论：本文主张，面向带宽受限的 Decode，HBM 容量达到模型权重与热 KV 的最低门槛后，继续堆叠 DRAM die 可能使系统成本增长快于有效 token 吞吐增长。但 4-hi 并非普适最优：高并发、长上下文、较大未来模型、训练与容错余量会改变结论。尤其要区分未来 NVL576 的理论模型和现有 GB300 的小幅 HBM 限制实验。

1. 文章信息与选文原因

原文标题：Long Live the Short King: Why 4-hi HBM Wins；中文标题：《矮堆叠之王：为什么 4-hi HBM 可能胜出》。

副标题译文：《带宽不减、裸片更少：4-hi HBM 如何降低推理成本并提高稀缺 DRAM 的利用效率》。

作者：Myron Xie、Bryan Shan、Harrison Barclay，官方页面另列 2 位作者但当前公开文本未完整展开；发布日期：2026-09-13；访问状态：标记 Paid，公开正文从导语至“Maximizing Tokens/HBM Wafer”可阅读；“Memory Supplier Impact”开始为付费墙，不分析付费正文。

2. 原文翻译与按章节中文转述

导语/摘要意译：HBM 随 AI 加速器代际发展持续增加堆叠高度和容量，消耗越来越多 DRAM 晶圆。作者认为这种趋势开始反转：未来部分产品从 12-hi 转向 8-hi，甚至推理专用芯片可能适合 4-hi。由于每 stack 的接口带宽主要由数据位宽和引脚速率决定，而不是简单由堆叠层数决定，降低容量可能大幅改善单位带宽成本和每片 DRAM 晶圆可支持的推理吞吐。本文试图证明一部分 HBM 容量实际上难以转化为有效 token 吞吐。

2.1 The HBM Content Trend is Broken｜HBM 容量持续增长的趋势出现逆转

原文先比较 SRAM（高带宽但容量受限）、DDR（容量成本低但带宽受限）和 HBM（折中）。作者称 Rubin Ultra 的 HBM 容量规划为每 GPU 192GB，而常规 Rubin 与 B300 为 288GB，并把该变化归因于 HBM 晶圆供给和成本压力，以及系统级容量余量扩大。这属于作者对产品路线的报道与判断，不能直接当作 NVIDIA 已公布的 Rubin Ultra 最终规格。作为对照，NVIDIA 当前公开的 Vera Rubin NVL72 页面列示普通 Rubin GPU 288GB HBM4（预备规格）。

2.2 Shorter Stacks, Same Bandwidth｜更矮的堆叠，相同接口带宽

作者讨论 HBM4/HBM4E 每 stack 2048 data I/O、每 DRAM core die 最多 512 I/O 的组织方式，提出 4-hi 是可充分覆盖 2048 I/O 的最低高度。在相同 I/O 位宽、每 pin 速率、时序与实现条件下，4-hi / 8-hi / 12-hi 的理论接口峰值带宽可相同，而容量随 die 数增长。不能将此误解为实测应用吞吐必然相同；bank 并行度、刷新、功耗、热和访问局部性可能影响有效带宽。

2.3 Bandwidth vs Capacity? Bandwidth is King｜带宽和容量：推理更偏向带宽

作者按预训练、后训练/RL、推理划分工作负载：预训练需存放权重、梯度与激活，对容量更敏感；Decode 反复读取活跃权重和 KV，通常更依赖带宽；RL 的 rollout 接近推理，但大 batch 又增加容量需求。大规模 NVLink Scale-up 让模型副本可跨大量 GPU 分片，使系统总 HBM而非单 GPU 容量成为关键变量。MoE Expert Parallelism 还会提高 All-to-All 通信，因此扩大的内存域与网络成本必须联合考虑。

原文举例：H100 HGX 总 HBM 640GB，Llama 3.1 405B 权重占比较高；GB300 NVL72 约 21TB HBM，Kimi K3 2.8T 在作者假设的 MXFP4 表示下模型权重约 1,561GB，占总量不足 8%。这说明特定量化模型的静态权重只占系统内存一部分；但不能据此认为其余容量都空闲，因为 KV、运行时缓存、碎片、并发副本与故障冗余同样需要空间。

2.4 The Optimal Mix of Bandwidth and Capacity｜带宽与容量的最佳组合

作者使用示例 HBM4E：2048 pins × 13Gb/s ÷ 8 = 3,328GB/s/stack；每 core die 32Gb 时，4-hi / 8-hi / 12-hi 分别为 16/32/48GB/stack。在 100 token/s 的单序列简化模型中，每 token 的峰值带宽预算为 33.28GB。以可用带宽除以 HBM 容量，衡量给定速率下理论上每 token 能扫过多少存储数据。这只是帮助理解的 roofline 代理指标，并非真实 decode 的通用性能公式。

作者随后加入 batching 与交互速率 SLA：更高 batch 能分摊权重读取，但需要更多每用户 KV 容量。吞吐上限由可容纳并发与带宽允许并发中较小者决定，二者与每用户 token/s 相乘得到总吞吐。大模型、高并发、低交互速率时，高容量 HBM 的价值上升；高交互速率、权重在大规模域内高度分片时，容量的边际价值下降。

在作者假设的未来 Rubin Ultra NVL576 + HBM4E 13Gb/s + Kimi K3 roofline 模型中，4-hi/8-hi/12-hi 为 128/256/384GB/GPU；105 tok/s/user 时 12-hi 对 8-hi 没有额外吞吐收益；213 tok/s/user 时高于 4-hi 的容量不再增加吞吐；最大总吞吐方面 8-hi 与 12-hi 分别仅比 4-hi 高约 8% 与 10%。作者模型假定 8-hi 与 12-hi 相比 4-hi 系统成本高 12.1% 与 26.3%，据此判断这组参数下 4-hi 的成本/token 更低。这些不是 Rubin Ultra 实测结果。

2.5 A Real Experiment: KVCache Offloading Relieves Capacity Pressure｜真实实验：KV 卸载缓解容量压力

作者在16 张 GB300 GPU的 Kimi K3 P/D 分离系统中测试，Prefill 8 张、Decode 8 张；把 HBM 利用率上限从 92% 调到 85%，并非实际将 8-hi 换成 4-hi。这样使单 GPU KV 预算减少约 20GB：Aggregate 模式 53→34GB，Disaggregated P/D 对应 44→24GB。多数并发点吞吐近似；当并发超过约 70 时，受限配置 KV 占用触顶，吞吐下降接近 30%，同时 DRAM KV 读取次数超过正常配置 10 倍。实验支持“适量容量压缩可被卸载吸收”，不支持“HBM 容量减半仍保持性能”的泛化。

2.6 Does 4-hi Give Up Future Proofing Optionality?｜4-hi 是否牺牲未来适应性

作者承认用当前 Kimi K3 预测未来 NVL576 的局限：设备寿命可能超过 5 年，模型与 KV 会增长。其反例设定模型和单用户 KV 同时扩大 3 倍：8-hi、12-hi 相比 4-hi 的最大总 token 分别提高约 36%、47%，但可能以较低用户交互速率实现；在部分低于 180 tok/s/user 的条件下，8-hi 的增量吞吐超过其增量成本。作者认为模型结构、循环 Transformer、RL 和软硬件协同设计可能抑制容量需求增长，这属于预测而非可保证的路线。

2.7 Maximizing Tokens/HBM Wafer｜最大化每片 HBM 晶圆支持的 token

作者把优化目标从 token/W 和 token/TCO 扩展到 token/DRAM wafer：同样的 DRAM die 供给，4-hi 理论上可组装更多 stack，从而交付更多总接口带宽；相比 8-hi/12-hi，简单 die 数计算分别是 2×/3×，封装良率还可能改变结果。但是否转化为实际 token 产出，取决于逻辑晶圆、base die、CoWoS、载板、整机集成、电力与软件可用性。最后公开章节提示付费部分将讨论存储供应商影响，本文不推测该部分。

4. 技术机制与硬件/网络影响

4.1 4-hi 不改变 pin 数，不代表系统吞吐不变

公式 B_peak = N_pin × R_pin / 8 与容量 C = N_die × C_die 分离，说明接口带宽与容量可以独立调整；实际 B_effective = B_peak × η 的 η 受内存控制器、bank 并行、访问模式、ECC、刷新、热约束等影响。工程选型必须同时量测持续带宽、P99 延迟、可用容量与功耗。

4.2 Scale-up 域扩张是内存优化的前提，不是免费的容量池

一个 576-GPU 域能摊薄每 GPU 权重容量，但 MoE EP dispatch/combine、tensor parallel collective、跨 GPU KV 定位与重传恢复会消耗互联带宽。对 GPU/IO-Die 规划而言，不能只以总 HBM 容量决定网络：要估算每 token 的 Expert All-to-All 字节、活跃 expert 数、并发、同步频率及尾延迟，并检查单个 Scale-up 域是否足够、跨域是否触发 Scale-out 流量。

4.3 P/D 分离改变 HBM 与 DDR 的成本边界

Prefill 和 Decode 的存储需求不同。Decode 可以把冷 KV 卸载到 CPU DRAM / SSD，热 KV 保留 HBM，但需要将迁移流量、页故障、PCIe/NVLink-C2C/网卡传输及队列拥塞纳入 SLA。若一个 token 步骤需要从低层内存回迁大量 KV，瓶颈会从 HBM 转移到 CPU 内存、主机链路或 Scale-out Fabric。网络侧必须区分一次性 P→D KV Transfer 与反复发生的冷 KV 回迁。

4.4 供给约束下的芯片组合优化

4-hi 降低每 stack DRAM die 数，可能提高同等 DRAM 晶圆可供应的加速器数量，但“2×/3×更多 stack”不等于“2×/3×更多 GPU”或“2×/3×更多 token”。需要核对逻辑 wafer、base die、先进封装、HBM 测试良率、基板、网络芯片与供电配额。高密度 HBM 在训练和高并发服务中仍可能有更高价值。

4.5 工程判断边界与建议

在定义 ASIC 或 GPU SKU 时，至少建立三组 workload envelope：低并发高 TPS、常规多租户并发、极端长上下文/大模型。对每组记录模型权重、KV/token、可用 HBM、HBM 实测带宽、P99 TPOT、PCIe/Scale-up/Scale-out 带宽、实际成本。对 4/8/12-hi 逐一计算 cost / successful output token 而非只比较峰值带宽/GB。为五年部署寿命加入模型增长与 KV 压缩的不确定性。

6. 值得验证的问题与一手来源

  1. 4-hi HBM4E 的 2048-bit 满速是否在量产控制器/封装上成立？查 JEDEC HBM4 标准、厂商 HBM4/HBM4E datasheet，比较实际每 pin 速率、温度、功耗、bank 并行与良率。JEDEC 标准检索。
  2. Rubin Ultra NVL576 的 192GB/GPU 与堆叠高度是否最终确认？当前 NVIDIA 公开的普通 Rubin NVL72 是 288GB/GPU；不能混同。NVIDIA Vera Rubin NVL72 规格页、NVIDIA CES 发布。
  3. 作者的 Kimi K3 Roofline 是否高估了带宽利用率？需要 HBM achieved BW、GEMM/Attention/EP 的分解、真实 batch、TPOT 分布；可与 InferenceX 的公开方法及测试交叉验证。
  4. KV 卸载的收益何时反转？量测并发超过 70 的突变点是否受 KV cache policy、CPU DRAM 读带宽、网络传输或 preemption 主导；将迁移字节/秒、miss ratio、P99 TPOT 联合画出。
  5. Scale-up 扩张是否消耗了节省的 HBM TCO？用 EP All-to-All、Link utilization、交换机成本、域故障半径和单请求完成率评估。
  6. HBM 晶圆产出优势如何折算为有效 token？向 HBM 供应商核实 core die 良率、base die、stack test、KGD、封装良率与 DRAM die 面积；把供给量转化为可交付整机而不是孤立 stack。
