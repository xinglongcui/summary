Post-training 能否直接复用预训练集群？

01｜结论：硬件可复用，不等于系统可原样复用

绝大多数 Post-training 不需要另建一套物理 Scale-up / Scale-out Fabric；但 Online RL，尤其长程 Agentic RL，需要新增推理、奖励、轨迹、状态恢复和调度等软件能力，并可能需要独立的 CPU/Sandbox 资源池。
层面能否复用工程边界
GPU / HBM / NVLink 或同类 Scale-up通常可以训练时继续承载 TP/EP/PP 等；Rollout 则采用推理式并行配置
IB / RoCE / Ethernet Scale-out物理网络通常可以需要校核 Policy Sync、轨迹传输、KV 迁移和新的长尾/Burst 分布
预训练框架与 Checkpoint部分直接复用Trainer 复用 FSDP/Megatron 等；在线 RL 需要接 vLLM/SGLang 和 Reward
调度、缓存、控制系统不能完全原样复用引入 Actor/Rollout/Verifier/Policy Version、KV Cache 与恢复机制
CPU / DRAM / NVMe / Sandbox按任务类型数学 RLVR 可以很轻；代码/Browser/仿真 Agent 往往需大规模独立隔离环境

设计判断 「资源池逻辑分离」不等于「购买独立 GPU 集群」，更不等于「必须设计新网络协议」。

02｜区分 SFT、离线偏好训练、Online RL 和 Agentic RL

工作负载训练方式相对于 Pre-training 的新增内容基础设施结论
SFTTeacher Forcing + Forward/Backward数据处理和 Loss/Mask 差异，通常无模型内生采样闭环基本复用原训练集群和网络
DPO / 离线偏好优化现成成对偏好样本的优化Reference Policy、额外 Forward/Log-prob仍非常接近普通训练；可能增加显存和计算
Online PPO/GRPO/RLVR生成 Rollout → Reward → Update推理服务引擎、轨迹 Buffer、参数同步与 RL 调度可以共址；需要 RL 专用软件栈
Long-horizon Agentic RL多轮推理 ↔ Tool/Environment，长轨迹，恢复Sandbox、状态快照、KV/Prefix、并发/尾延迟优化物理 GPU 网络可复用，但环境和状态服务必须专门设计

反例很重要：后训练不是一个统一工作负载。不能把 Agentic RL 的 CPU Sandbox 和异步流量要求，强加到普通 SFT 或短推理 RLVR 上。

03｜从网络架构看：哪些仍然沿用预训练 Fabric？

3.1 Scale-up：训练部分几乎延续原通信要求

Policy Gradient Update 仍需执行模型 Forward/Backward。对大型 MoE 而言，训练 TP/EP/PP 和跨节点 DP 的通信需求仍然存在。已有 NVLink/NVSwitch 类 Scale-up 和 RDMA Scale-out 依然有价值；Online RL 并不会消灭训练网络。

但 Rollout 是推理：它更关注 Decode、KV 容量、Prefix 命中与动态并发，可能使用与训练不同的 TP/EP 配置。两者在同一个物理 GPU Group 上切换时，需要重载权重、释放/恢复 KV 或重新配置资源，不能当成同一个 Kernel Pipeline。

3.2 Scale-out：能承载，但业务不再只有训练 Collective

现有 Ethernet/RoCE/IB 通常能承载新业务，无需专门的“RL 网络协议”。然而 带宽容量够不表示共享拥塞下的性能也够。

工程需要重新校核：Policy 权重广播/同步、Checkpoint 与缓存访问、Long-rollout 恢复时的 KV/State Burst、CPU Sandbox RPC（对 RTT 敏感）、在线训练 Collective（对尾延迟敏感）。若共用一个承载面，需做工作负载隔离、优先级和队列观测；但不能一概要求所有 RPC 使用无损 RDMA。

3.3 不推荐简单增加一个巨大 Scale-up Domain

训练时紧耦合的模型并行组可以利用低延迟 Scale-up；CPU Sandbox、Trajectory Store、验证器和 Rollout 的跨池控制流没有天然的 Load/Store 同域需求。把所有计算资源塞入单一 Scale-up Fabric 不能从 Agentic RL 本身推导出来。工程推断

04｜三种现实可选架构

A. Co-located 共址 / 分时同一组 GPU 在 Rollout 与 Update 间切换

优点：易复用已有训练 GPU、避免远程大规模权重分发、减少闲置；代价：HBM/DRAM/KV 竞争、阶段切换、长尾阻塞。

B. Disaggregated 物理解耦训练 GPU 池 + Rollout GPU 池 + CPU 环境池

优点：各阶段可独立调度，异构设备按计算/带宽适配；代价：Policy Sync、额外传输、版本陈旧、资源利用率平衡。

C. Hybrid / Elastic 混合架构

部分 Rollout GPU 常驻，部分 Training GPU 在等待数据时临时提供 Rollout 算力。verl 的动态资源调度文档已公开这种 Standalone + Hybrid 组合，并有特定模型下 15.3% 端到端训练时间缩短的实验结果。这意味着不需要以「全共址」和「全解耦」二选一。[6]

已有预训练集群：GPU + Scale-up + Scale-out + Storage
↓ 物理资源保持复用，增加角色与调度
Training GPU（Policy/Gradient，继续使用原训练通信）
⇅ Policy Weights / Version、Trajectory
Rollout GPU（vLLM / SGLang，Decode、KV、Prefix）
⇅ Tool Requests / Results
CPU Sandbox / Verifier / DRAM + NVMe State

图示是逻辑资源层次，不是强制物理布线。三个角色既可以共享服务器/机柜，也可以位于独立的节点或资源池。

05｜新增通信与现有网络的适配性

流量类型已有训练网络能否承载变化点 / 主要风险
TP/EP/PP/DP 通信✓ 原有 Fabric 继续使用同步 Collective / All-to-All；保证训练 QoS，不被其他业务挤压
Policy Weight Sync✓ RDMA / Ethernet 可承载可能是高体量周期性 Fan-out，负担取决于分片/副本数/同步频率
Rollout KV / State Resume✓ 依部署模式而定GPU↔Host 或跨节点，可能出现集中恢复 Burst；不是所有部署都有跨网络传输
Trajectory / Reward / Logprobs✓ 现有网络与存储大小不规则、版本一致性与队列拥堵，通常非低延迟 Load/Store
Sandbox Tool RPC / Filesystem✓ TCP/IP / 存储网络大量小交互、冷启动、镜像读取、快照 I/O；可能需要独立 CPU/IO 容量

5.1 权重同步的数量级：不要误以为每卡搬运全模型

以 Kimi K3 披露的 2.8T 总参数为例：若全部权重采用 BF16，逻辑数据约 5.6 TB。这个值只是整个模型全量权重的规模上界示意，绝不等于每张 GPU 的搬运量，更不等于每一步跨机架网络必须传输 5.6 TB。实际同步量由权重切片、增量/量化、原地共址、复制副本数量和频率决定。[1]

Dsync ≈ Sshards × Ncopies × Fsync（每单位时间）

其中 Sshards 是每次实际传送的切片量，而不是默认全模型。需要按实际通信路径去重，广播树、多播、分层分发、重复缓存都会改变链路负载。

5.2 KV 恢复的判断逻辑

KV 从 GPU 驱逐到同节点 CPU DRAM 时，主要约束 PCIe/NVLink-C2C 及内存/IO 带宽；只有状态真正跨节点迁移时，才成为 Scale-out Fabric 的 KV Traffic。设计网络前必须先确认 KV Owner / Cache Locality / Migration Policy。

不要混淆：P/D 分离推理中的 Prefill→Decode KV Transfer，与 Agentic RL 跨 Rollout/Iteration 的 KV 持久化恢复不是同一个生命周期；可能共用传输组件，但业务发生时间、方向和 Burst 都不同。

06｜决定是否单独建设基础设施的准则

需要同时量化四个问题：

  1. Rollout/Training 资源占比：生成轨迹的耗时能否被训练 GPU 同步/分时消化？
  2. 模型权重同步代价：分离之后新增的网络时间是否抵消异步重叠收益？
  3. Sandbox 数量：环境启动、CPU、DRAM、NVMe、外部网络和检查器是否构成独立瓶颈？
  4. 长尾与状态：轨迹 p95/p99、恢复次数、Prefix 命中与 Policy Staleness 是否损害吞吐/收敛？
Tcolocated ≈ Trollout + Tupdate + Tswitch
Tseparated ≳ max(Trollout,Tupdate) + Tsync-unhidden + Tstall

上式是稳态周期的简化性能模型，不含复杂资源数量与环境端约束。若 Environment 更慢，实际瓶颈还要纳入其处理能力；异步 Off-policy 对收敛质量也有可能付出代价。

适用条件优先方案理由
现有训练资源充裕；SFT / 短 RLVR；预算敏感共享训练集群 / Co-located低改造成本，不急于专门建 Rollout Fabric
Rollout 占大部分总时间，长尾严重，训练 GPU 明显闲置Hybrid 或 Disaggregated利用生成与训练重叠，提高端到端吞吐
大量代码执行、网页交互、环境重启/快照单独 CPU/Sandbox Pool隔离安全和 IO 负载，避免占用高价 GPU 计算资源
超大 MoE、频繁 Policy 更新、跨节点全量同步很贵先测 Co-located / Hybrid避免假设分离必然带来好处

07｜公开系统提供的证据：共址与分离均已验证

Kimi K3：共址方案并非过时

Kimi K3 技术报告 §5.3.1 描述：在百万 Token Agentic RL 中采用 Co-located 训练和 Partial Rollout；为长前缀提供 GPU/Host 分层缓存与 Write-back；并使用可恢复的 Sandbox 运行环境。报告明确其目标是在数百 GPU 规模下进行单项长上下文 RL 实验。[1]

事实 共址 + KV/State 分层，是已经公开的工程路线。
局限 报告没有公开完整网络拓扑与 RL 生产集群流量矩阵，不能据此得出“原预训练 Fabric 在任何规模下完全不用改”的结论。

verl：训练框架、推理后端可以共享 GPU 和网络

verl 的 Hybrid Engine 将 Actor、Rollout、Reference 组合在 GPU Worker 内，训练使用 FSDP/Megatron 等，推理使用 vLLM/SGLang。官方文档指出共址的重要原因是利用 NCCL 实现快速权重传递；另一方面也支持独立设备映射和异步执行。[2][3]

NVIDIA NeMo RL：现有 Slurm/Ray 环境既能共址也能分离

NeMo RL 官方示例明确支持 Policy 与 Generation Colocated，也支持放在不同 GPU/节点。其 Dynamo 试验性集成使用 Slurm + Ray，在统一资源分配下部署独立 vLLM GPU Fleet，并用 NCCL 实现 Policy Update。[4][5]

RollArt（OSDI 2026）：分离式方案适合规模化多任务

ROLLART 将 Prefill、Decode、CPU Environment 和 Reward 按硬件特征调度，允许轨迹级异步与有限策略陈旧。论文报告相较其对照 RL 系统训练时间缩短 1.31–2.05 倍，并在阿里巴巴超过 3,000 张 GPU 集群上对数千亿参数量 MoE 训练进行了验证。[7]

工程推断 这说明大规模 RL 可以建设异构资源池，但论文并未证明所有模型/工作负载都应该独立建物理网络。

08｜若以现有预训练数据中心改造，推荐这样做

优先级改造项目判断标准
P0保留原 Scale-up/Scale-out；部署 RL Trainer + vLLM/SGLang先以 Co-located 建立可运行基线
P0配置 Reward、Trajectory、Policy Version、Checkpoint能重放/审计一条完整训练轨迹
P0按业务选择 CPU Sandbox/Verifier代码 Agent 必须可安全隔离、暂停和恢复
P1网络分流/QoS 和 Telemetry分开观察训练 Collective、Weight Sync、KV/State、RPC 的 p95/p99 和 Burst
P1对比共址、混合、解耦三种基线比较每单位成本下的有效训练收益，而不只比较 MFU
P2仅当测量显示瓶颈时，升级或独立建设 Fabric/资源池基于容量、延迟、拥塞和稳定性实测，而非“RL 必须独立部署”的假设

建议采集的最小指标：Rollout/Update/Sync/Environment 时间占比、GPU Active Ratio、完成轨迹每秒、Trainer 等待比例、Weight Sync Bytes 与周期、Rollout p99 长度、KV Hit/Migration、Sandbox 启停/快照 P99、网络队列拥塞、Policy Staleness、模型任务成功率。

最终架构判断：复用现有训练网络是合理的默认起点；需要独立的是 RL 运行时的角色和状态管理体系；是否建设专用 Rollout GPU 池或新物理 Fabric，应由负载测量与端到端成本收益决定。
