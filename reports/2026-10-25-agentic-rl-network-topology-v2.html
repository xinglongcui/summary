01｜直接结论

Agentic RL 不是只有“一张训练网”。至少要逻辑区分 Scale-up GPU 网络、Scale-out RDMA/数据平面网络、机头/In-band 网络、OOB 带外管理网络、业务/服务网络、存储网络。其中：训练 Collective、权重同步、跨节点 KV/状态搬运 不应该跑在机头网络；Head/In-band 管理网络负责控制面；BMC 由 OOB 带外网络单独承载。
Scale-up节点内或超节点内的 GPU 紧耦合网络，例如 NVLink/NVSwitch/UALink。承载 TP/EP/PP 等高频张量通信。
Scale-out节点间高带宽数据平面网络，例如 IB、RoCE、AI Ethernet。承载跨节点训练通信、权重同步、部分跨节点状态流。
机头/In-band 管理网络承载 Head Node、Slurm/K8s/Ray 控制、SSH、监控等。BMC/IPMI/Redfish 应另归 OOB 带外管理网络，两者不能混为一谈。
业务/服务网络CPU Sandbox、Mock API、DB、Reward Service、Web Service 之间的东西向 RPC。关注并发、RTT、长尾。
最常见错误：把 Policy Weight Sync、Checkpoint 大文件、Sandbox Tool 大量结果 也塞到机头网络。这样很容易把调度、健康检查和控制面一起拖垮。

05｜设计规则

  1. 机头/In-band 管理网络优先承载控制面；BMC 走隔离的 OOB。 任何可预见的大流量都不要默认走机头网络。
  2. 训练数据面和业务服务面要区分。 即使物理共网，也要通过 VLAN/QoS/队列逻辑隔离。
  3. 先判断流量是不是“张量流”。 不是所有 RL 数据都值得放在 RDMA Fabric 上。
  4. 权重同步要单独测。 它可能成为 RL 区别于传统预训练的新增大流量。
  5. 工具 RPC 的问题通常不是带宽，而是 p95/p99。 例如浏览器、编译、DB 查询、外部 Mock 服务容易形成长尾。
  6. 存储流量不要和控制面打架。 Checkpoint、镜像拉取、日志归档应该有明确出口。

06｜两种典型部署怎么映射？

A. Co-located 方案

Trainer 和 Rollout 复用同一组 GPU。此时：

  • 训练 Collective 主要在 Scale-up/Scale-out 上；
  • Weight Sync 可能退化为本机显存重装，不一定经过交换机；
  • Sandbox / Reward 仍走 业务/服务网络；
  • Checkpoint / 镜像仍走 存储网络；
  • 调度、健康检查仍走 Head/In-band 网络；BMC 走独立 OOB。

B. Disaggregated 方案

Trainer GPU Pool、Rollout GPU Pool、CPU Sandbox Pool 分离。此时：

  • Weight Sync 成为最关键的 Scale-out 流；
  • Rollout ↔ Sandbox 的工具交互主要在 业务/服务网络；
  • 若 Prefill/Decode 分离，P→D KV 可能也是 Scale-out 上的重要流量；
  • Trajectory/Reward 在 Buffer 服务化时也更多依赖 业务网；
  • Head/In-band 网络做控制面，不承载 GPU 热数据路径；BMC 走 OOB。
所以：“整个 RL 的业务流”不是只跑在一张网里，而是跨多张逻辑网络协同。 真正要做网络规划时，建议把每条流量先归类，再映射到物理 NIC、ToR、Spine 和存储出口。

07｜按照单机柜、跨机柜/Row、跨 Pod 划分的物理网络拓扑

定义与适用范围：这里的 Rack 是物理机柜，Row 是数据中心机柜排，Pod 是由网络/计算资源组成的拓扑组织单元，不是 UALink Switch API 中的 vPod。本报告的“Scale-up”指低延迟 GPU 紧耦合域；它可能跨机柜，因此不能机械等同于单机柜。以 NVIDIA GB200 为例，NVLink 域可覆盖整柜；未来的其他 Scale-up 方案可能跨多机柜。[S1]

A. 单机柜：GPU 侧至少区分四种端口语义

Compute NIC 与 Scale-up Link 是两类不同的数据出口。Head Node 使用 In-band Host/Front-end 网络；BMC 网络应独立隔离。Storage 可以使用专用 NIC/DPU/交换机，也可能与业务网络在物理基础设施上复用但用 VRF/VLAN/overlay 等隔离。

B. 跨机柜 / 跨 Row：分别沿 Compute、Services、Storage 三条路径走

跨柜 GPU 张量通信的典型逻辑是 Compute NIC → Compute Leaf/ToR → Spine → 对端 Compute Leaf → Compute NIC。Tool RPC 则可经 Host/Services 网络；Checkpoint 则走存储 Fabric。实际网络设备并非总是三套物理交换机，图中拆分的是流量平面。

C. 跨 Pod：计算数据是否跨 Pod，首先由资源编排决定

如果 Training 和 Rollout 放在不同 Pod，Weight Sync 需要跨 Pod 数据路径；如果二者在同一个 Pod 甚至同一个 Node，就不会出现此类跨 Pod 流量。跨 Pod 路径可由 Spine/Core/Super-Spine 承载，不能自动推导出需要跨 Pod 的单一 GPU Load/Store 域。[S1]

网络术语特别说明：“机头网络”不是厂商统一定义。通常它是 Head Node/调度系统的 In-band 管理网络；OOB 带外管理用于 BMC、IPMI/Redfish、交换机管理端口、PDU 等，安全域应区别于 Head Node。NVIDIA SuperPOD 将 Compute、Storage、In-band、OOB 分别建模，且支持共享 Ethernet 底座上的逻辑分段。[S1]

P0–P3 只是概念上的相对等级，并不是厂商推荐的 802.1p/DSCP 编号。Compute Lossless 网络中 PFC/ECN、优先级和队列模型必须统一规划，不可简单把所有 P0 业务塞进同一个无损队列。Services/In-band 与 OOB 通常必须有安全隔离，后者不承载业务 Tool RPC。

建议以“完成时间分布”而不是单纯 Mbps 作为判断依据

  • Collective：Latency/FCT p99 + 有效 GPU 等待时间。
  • Weight Sync：每次 Refit 的 Makespan、并行度、每条路径 Bytes。
  • KV：TTFT、ITL、KV Transfer FCT、恢复 p99。
  • Tool RPC：网络 RTT 与业务计算时长拆开，观察短请求和大结果两类流量。
  • Checkpoint：完成时间、存储带宽和占用的前台业务容量。

09｜从“逻辑数据量”映射为机柜/Pod 物理带宽的工程示例

条件性估算，非厂商实测 以 32B BF16 Model、8 份完整逻辑推理副本、每 5 分钟 Refit 一次为例：

单份权重 ≈ 32 × 10⁹ × 2 B = 64 GB；8 份总逻辑分发 = 512 GB
平均等效业务速率 ≈ (512 GB × 8) / 300 s = 13.65 Gb/s（全系统总量）
若集中在 20 s 内完成，则等效总速率 ≈ 204.8 Gb/s（瞬时平均）

这里的 204.8 Gb/s 不是任意单根上联的必需带宽。若分发采用 Host/ToR 内的缓存复用、分片、分层广播，单根跨 Pod 链路可能只承载一部分或一次模型数据；如果所有副本逐一经过同一瓶颈链路，压力就明显更大。

再假设独立 GPU KV Resume：64 条轨迹各需跨节点恢复 4 GiB，并希望 8 s 内完成（仅示例）：

64 × 4 GiB / 8 s = 32 GiB/s ≈ 274.9 Gb/s（总有效载荷）

若同一批状态全部在本机 Host DRAM，则这些字节不经过 Scale-out ToR，其瓶颈可能在 PCIe / CPU DRAM / 本地加速器互联。

最后考虑 Tool RPC：2,000 次/s × 每次 Request+Response 16 KiB，则整个 Service Network 的平均载荷约 262 Mb/s；但若每轮工具调用必须等待上一轮结果，哪怕带宽空闲，RPC p99 增加也会显著拖慢长程 Trajectory。

正确的容量规划步骤

  1. 定位每份 Policy Replica、KV Owner、Sandbox 和 Buffer 的机柜及 Pod。
  2. 标出 NIC/DPU（Compute、Host/In-band、Storage、BMC）对应哪张 Fabric。
  3. 对每一条 Flow 建立 source / destination / bytes / fan-out / burst window / deadline。
  4. 将逻辑 Flow 映射到具体 ToR、Spine、Core 与 Rail，沿路径累计 Bytes（考虑复制树）。
  5. 把 G1、F8、O1/O2、F2/F3、O3 的时间序列叠加，在真实拥塞控制下分析 P95/P99 和边界条件。
关键结论： Agentic RL 对 Scale-up 主要延续模型并行通信需求；对 Scale-out 增加 Policy Weight Sync、可选 KV 迁移和恢复突发；对 CPU/业务网增加高并发 RPC；对 Storage 增加 Snapshot/Checkpoint；而 Head/In-band 与 OOB 需要独立保持可用和安全。网络建模的核心是路径与时间重叠，而非只罗列峰值带宽。
