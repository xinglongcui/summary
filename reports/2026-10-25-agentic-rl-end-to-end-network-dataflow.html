01｜先说结论：RL 的网络并非一种流量，而是至少七条相互交织的数据路径

Online RL 的主循环是：训练任务产生 → GPU Rollout 模型执行 → 与 Sandbox 多轮交互 → Verifier 给 Reward → Trajectory 被训练 GPU 消化 → 得到新 Policy → 权重重新部署到 Rollout GPU。循环反复执行。真正的大流量可能发生在「模型内部训练通信」和「跨资源池权重同步」，而环境工具调用通常是小消息、高频、对异常和尾延迟敏感。
主数据循环Task → Action/Observation 多轮 → Trajectory → Reward → Advantage → Gradient → 新权重。
两套不同的数据平面GPU 训练/推理 Tensor 通信；跨 GPU/CPU/存储资源池的业务对象和控制通信。
最容易误判的点Token 序列并不是 KV Cache；GPU 与同机 CPU 内存拷贝不等于网络流量；Gradient 同步不等于 Policy Weight Sync。
架构关键条件是否 Co-located？Rollout 是否 P/D 分离？Policy 几个版本同步一次？KV 状态在本机还是远程？

已验证 verl、NeMo RL 和 OSDI 2026 RollArt 均明确描述了 Rollout、Reward、Policy Training、Refit/Weight Sync 的可分离阶段；其具体部署并不唯一。[1][2][3]

03｜一次完整 GRPO / Agentic RL 迭代：业务动作和网络动作逐步对应

阶段执行什么业务生成/消费的对象网络数据方向
0. 启动（不是每步都做）预训练/上次 RL Checkpoint 恢复；拉起 Actor、Rollout、Environment模型权重、Optimizer 状态、镜像、任务池共享存储 → Training GPU / Rollout GPU；镜像 → CPU Sandbox

8. 训练数据准备GRPO 组内归一化优势；PPO 可选 Critic/Value；计算 old/ref logprobstoken/mask/advantage/logprob/value 等 TensorSample Buffer ↔ Training/Ref/Critic GPU；部分模块可同址
9. Policy 更新Loss、Forward/Backward、Optimizer StepActivation、Gradient、Optimizer State、新权重训练 GPU 组内部 NVLink/IB/RoCE Collectives

三个容易混淆的“完整体”

  • 一个 Turn：模型观察当前上下文并发出一次回复/工具 Action。
  • 一个 Trajectory / Rollout：一个任务从初态到终止，包含许多 Turn、Action 和 Observation。
  • 一个训练 Step / Iteration：聚合一批 Trajectory、打 Reward、算优势和梯度、更新 Policy；异步系统中 Rollout 与 Training 可以重叠，不一定严格一轮一轮等待。

已验证 verl 官方 PPO 代码流程逐项列出 generate_sequences → compute_log_prob → compute_ref_log_prob → compute_values → compute_scores → advantages → update_actor/update_critic，NeMo RL GRPO 则支持不使用独立 Critic 的路径。[1][2]

05｜GPU 内部网络：和预训练比，哪些流量其实没变？

RL 的 Actor Policy Update 阶段仍然是在做大模型训练，TP/EP/PP/DP 等通信模式与传统预训练非常接近。只是每轮样本来自模型自身 Rollout，而不是固定网页语料。对 MoE 模型，EP Token Dispatch/Combine 与负载均衡问题仍然存在。

Training GPU 侧TP：跨并行卡交换部分计算结果。EP：MoE Tokens All-to-All。PP：Activation/Gradient 边界传递。DP：Gradient/Shard 同步。高同步强度，Scale-up/Scale-out 性能关键。
Rollout GPU 侧Prefill 的 Matmul + 可能较大 EP Token Burst；Decode 的逐 Token/小 Micro-batch、KV 读写、TP/EP 通信。并行策略可独立于 Trainer。
反例：如果每个 Rollout Replica 能完整装下模型且不使用跨 GPU TP/EP，那么其 GPU 内部网络需求可能很低。不能把“有 1000 条 Agent Trajectory”直接等价于“需要 1000 GPU All-to-All”。

Gradient 同步 ≠ Policy Weight Sync

前者发生在 Trainer 的梯度更新内部，每个训练迭代有多次 Collective；后者发生在 训练模型更新后到推理模型的部署，取决于部署拓扑和 Refit 频率。前者可以全部走原训练 Fabric，后者可能跨两组独立的 GPU Fabric。

06｜Policy Weight Sync：可能是 RL 新增的最大跨资源池网络负载

Weight Refit 不是传统 DP AllReduce，也不是每次都保存 Checkpoint。它要求把训练策略最新参数以适合 Rollout 推理引擎布局的形式，送到一个或多个推理副本。

部署常见权重路径网络特征
Co-located同机 GPU/进程 → CUDA IPC、GPU 显存重排、模型唤醒可减少跨网络搬运，但产生权重重装、HBM/显存竞争与阶段切换
Disaggregated / 高速网络Trainer GPU → Rollout GPU，经 NCCL Broadcast/Reshard 或 NIXL/UCX大对象、周期性集中 Fan-out；源端、多目的 GPU、网络链路要按拓扑核算
Disaggregated / 异构网络Trainer → CPU Store（权重 Bucket）→ Rollout 集群内 Pull跨集群“写一次、集群内多副本拉取”，减少反复穿越较慢跨池链路
压缩/稀疏更新（受实现约束）Sparse Delta / 压缩 Transport实际数据量可能降低；不能假定所有算法/模型支持

已验证 NVIDIA NeMo RL 的 Weight Refit 官方指南列出了 Colocated CUDA IPC、NCCL、NCCL Reshard、Sparse Delta、NIXL 等路径及兼容限制。[4]

已验证 RollArt §6.3 在跨集群部分使用 Mooncake，权重先按例如 1GB Bucket 写到 CPU Resident Store，Rollout 再从集群内拉取；支持与持续 Rollout 重叠。[3]

Aggregate logical distribution volume ≈ Model bytes × Number of full replicas

如果仅从逻辑上考虑一个 32B 参数模型、BF16 权重：每份约 64 GB；如果有 4 份完整推理副本，逻辑总写入量约 256 GB。这不是“单根链路 256GB”，物理链路流量取决于模型分片、共享缓存/树形广播、复制层次和传输重试。分层重分片会重新决定每条链路的负载。

07｜RL Rollout 与 P/D Disaggregation：两种不同的状态流量

RL 训练本身不要求 Prefill/Decode 物理分离。如果 Rollout 在同一个推理实例内完成 P/D，则 KV Cache 留在该实例 HBM 中，不产生 P→D 网络传输。

只有选择 P/D 分离时，才有 Prefill GPU → Decode GPU 的 KV Transfer；当前 vLLM 明确提供 KV Connector 来协调两端缓存传输。[5]

另一条状态流量来自长程 Agent 的暂停/恢复：空闲 Trajectory 的 GPU KV、执行状态或 Sandbox 快照可能搬到 Host DRAM、远端 DRAM 或 NVMe。此时需要判断状态迁移是否跨节点。如果仍在同一台服务器，可能只有 PCIe、CPU Memory 或 NVLink-C2C 负载，而不是 Ethernet/RDMA Fabric 流量。

图示是逻辑路径，不代表 P/D 的 KV 必须写入 CPU Store，也不代表 CPU Store 能不经对应 Runtime 直接跨任何 GPU 格式共享 KV。

8.4 真实大规模任务的长尾

RollArt §8 报告其在 3000+ GPU 生产规模下的数千亿参数 MoE 训练，真实任务涉及 1–48 Turn；某些任务响应长度的最大值达到均值的 5–9 倍，环境交互 Turn 最大值超过均值的 40 倍。某些迭代中 Trainer 因等待 SampleBuffer 凑足轨迹而空闲，占迭代时间最高达 62%。[3]

对网络架构而言，重要的不是只按「平均 Token/s」计算带宽，而是把 Policy Weight Fan-out、任务提交/结果长尾、状态恢复 Burst 叠加到同一物理网络的时间轴，再分析队列和尾延迟。

09｜可调估算：一轮 RL 究竟会搬运多少数据？

以下简化工具可以在手机浏览器直接修改参数。它估算逻辑业务数据量，而非自动等于交换机端口流量。没有做网络协议开销、梯度通信、KV 移动、分片重排或重传建模。

一轮 Rollouts 数512
Trajectory 主张量大小131 MB
一份模型权重大小64 GB
副本总逻辑权重分发量256 GB
均摊权重分发逻辑速率3.41 Gbps
Sandbox 工具 RPC 合计速率65.54 Mbps

计算口径：MB/GB=10³ 进制；KiB=1024 字节。Trajectory 对象只算平均 Token 数×选定单 Token 字节数，不计额外 Prompt 文本、Tool Log、Reward 模型输入、图片或多次中间缓冲拷贝。权重分发速率 = 逻辑字节总量×8/同步周期；不是某根交换机链路的必需带宽。真实硬件要映射每个 Replica 的 TP/EP Shard、传播树、数据路径和发散时间。

Traj_bytes = Tasks × Group × AvgTokens × Bytes/token
Weight_sync_avg = Params × Bytes/param × FullReplicas / Interval
Tool_RPC_avg = Aggregate Calls/s × (Request+Response Bytes/call)

一个对比：默认示例中，训练样本主张量仅约 131 MB，而一次向 4 份逻辑 Replica 分发 32B BF16 权重为 256 GB。但这不说明它们经过同一根链路。若 Trainer/Rollout 共址、或先写一次 CPU Store 再内部广播，交换机跨池带宽需求可能显著不同。

10｜对 Scale-up / Scale-out 架构设计的直接结论

架构主要跨 Fabric 流量优点主要代价
Co-located训练 Collective；环境 RPC；Checkpoint（部分同机）Weight Refit 更靠近 GPU 内部搬运；复用训练物理 FabricRollout 与 Training 时间复用，HBM/内存竞争，长程轨迹管理复杂
Disaggregated训练 Collective + 权重跨池 Fan-out + Trajectory/Reward + Tool RPC + 可选 KVTrainer / Rollout / Env 可以并行、异构最优部署权重更新与 Policy Staleness；跨网络链路负载新增
Hybrid / Elastic随资源编排变化按训练/推理占比动态搬移资源，提高整体利用率的可能性状态归属、带宽规划和调度边界更难预测

对网络芯片研究最重要的四点

  1. 训练 Scale-up Fabric：核心仍是 TP/EP/DP 通信，Agentic RL 不自动要求扩大 Load/Store 物理域。
  2. 训练 ↔ 推理跨池 Fabric：需要分析权重广播、Reshard、版本更新频率、大流量 Burst 以及队列和 PFC/ECN 交互；若共享现有 Fabric，须避免影响训练 Collective。
  3. 推理内部 Fabric：是否 P/D 分离、EP/TP 是否跨机、KV 是否跨节点，决定网络内部是否出现较大 KV Transfer 与高频同步。
  4. CPU Environment 网络：不一定需要 RDMA 或专门 Scale-up，关键是稳定 RTT、RPC 并发、超时、Sandbox 重启与存储快照长尾。

工程判断 不应该一开始就为 RL 设计一张“全新的专用高带宽网络”；更合理的方法是从 Workload Matrix 出发，确认是否物理共址、每个通信流具体经过哪些 NIC 和交换机，再定位不可接受的瓶颈。

建议建模方法：先对每个物理 Fabric 定义节点与链路，再将 F1–F8/G1–G2/O1–O3 映射到源、目的、数据量分布、时间序列；最后分别计算平均速率、95/99 分位瞬时速率和流完成时间（FCT）。对于 TCP/RDMA 共用网络，需分析拥塞传播、队列优先级、ECN/PFC 与 Collective 之间的相互影响；这些必须在明确 NIC/交换机/拥塞控制配置后才能闭合。

研究结论：Agentic RL 新增的核心网络问题不是“所有 GPU 都进行 RL All-to-All”，而是高同步训练通信 + 大体量周期性 Policy 同步 + 高并发小对象环境 RPC + 可选 P/D KV 与长程恢复 Burst如何在时间上叠加及隔离。
