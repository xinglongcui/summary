研究摘要

大模型在后训练阶段的竞争正逐渐扩展为三项耦合能力：可扩展的 RL 学习、可靠的长程任务执行、以及能支撑长轨迹的异构基础设施。

问题一：RL 是否有独立 Scaling Law？在特定底座、任务集和训练配方下，可以拟合有预测力的经验计算—性能关系；但收益会饱和，不能证明追加 RL FLOPs 能无限突破能力边界。
证据判断：较强（受实验设置约束）。
问题二：长程 Agent 的核心瓶颈？不是简单的 Context Length 不够，而是任务状态维护、错误传播、验证反馈与恢复能力。仅增加工具调用和 Thinking Tokens 不保证改善成功率。
证据判断：较强（任务依赖明显）。
问题三：下一代 Agentic RL 架构？Train / Rollout / Environment 将趋向更细粒度的资源解耦和联合调度；但 Co-located、Disaggregated、Hybrid 的最优点取决于模型大小、同步频率、状态搬运量和成本。
证据判断：系统趋势较强，通用最优方案尚未确定。
RL 计算规模扩大 → 需要更多有效训练经验 → 需要更可靠的长程交互和可验证环境 → 改变 GPU、内存、存储和互联网络的负载结构。

01 · RL Scaling Law 是否独立成立？

结论：目前更准确的说法是「存在可预测、条件性的经验 Scaling 规律」，而不是「只要持续增加 RL 计算就必然持续提升能力」。

必须区分两个概念：Compute Efficiency（单位计算获得性能改进的效率）和 Asymptotic Capability（训练趋于收敛时的能力上限）。一个方法可能让模型更快到达 70% 的成功率，却未必让最终上限从 80% 提高到 90%。

1.1 大规模实验与 Scaling 曲线

证据 A：ScaleRL——训练计算与性能的经验可预测性

ICLR 2026 相关研究 The Art of Scaling Reinforcement Learning Compute for LLMs（文末资料 [1]）累计使用超过 40 万 GPU-hours，并通过约 10 万 GPU-hours 的单次大规模训练检验外推。论文报告：稳定 RL 过程可呈现具有预测性的计算—性能曲线；不同训练设置可能具有不同渐近性能；损失设计、归一化、Curriculum 和 Off-policy 处理等因素可显著改变效率，而未必改变最终上限。

可用一个具有饱和性质的简化 Sigmoid 形式说明：

R(C) = R0 + (Rmax − R0) / [1 + (C50 / C)b]
  • C：累计 RL 训练计算量；R(C)：相应性能。
  • R0：初始性能；Rmax：渐近性能上限。
  • C50：提升区间中点对应计算量；b：曲线形状参数。

工程含义：在固定基础模型、数据、奖励和算法的情况下，继续投入算力可能遇到边际收益快速下降。改变环境分布和训练目标，可能比机械增加 FLOPs 更重要。

证据 B：模型规模与 RL 效率

ACL 2026 论文 Scaling Behaviors of LLM Reinforcement Learning Post-Training（原回复引用）研究了 Qwen2.5 系列 0.5B 到 72B 模型，报告更大模型通常具有更高的数据与计算效率，并观察到可能的饱和趋势。这与前述结果不必冲突：训练的一段局部区间可拟合幂律，而有界性能指标的完整收敛过程可以呈 Sigmoid 式饱和。

1.2 争议：RL 能否突破基础模型本来不具备的能力？

观察口径研究发现应如何理解
Pass@1RL 往往明显改善单次正确率部署价值较直接
Pass@k某些研究观察到基础模型在足够大 k 时可超过 RL 模型RL 可能主要提升正确路径采样概率，未必扩大所有候选路径的覆盖
CoT-Pass@k另一些研究在同时验证过程与答案的指标上观察到 RL 提升「是否具有新的正确推理能力」取决于测量定义
Agent Task Success衡量是否真正完成环境中的任务对工程产品更直接，但测试基准和 Harness 会影响结果

NeurIPS 2025 论文 Does Reinforcement Learning Really Incentivize Reasoning Capacity in LLMs Beyond the Base Model? 提出 RL 可能主要重排既有推理路径的概率分布。ICLR 2026 的 Reinforcement Learning with Verifiable Rewards Implicitly Incentivizes Correct Reasoning in Base LLMs 则通过更重视中间推理正确性的 CoT-Pass@k 得到能力提升证据。

二者并非简单地一真一假。重要的是对「能力」作精确定义：单次正确率、探索覆盖、推理过程正确性和环境任务完成率并不等价。

RL 是否普遍创造全新的推理机制，尚无统一定论；RL 能改善策略选择效率和实际任务成功概率，则有较充分实验依据。

1.3 Environment Scaling：为什么环境多样性可能比算力更重要？

ICML 2026 的 RLVE 研究构建 400 个可验证环境，并根据训练阶段调整任务难度。在其 1.5B 级模型实验设置下，扩展环境覆盖带来了平均 3.37 个百分点提升，而继续原有 RL 训练、消耗超过三倍计算量，报告的改善仅为 0.49 个百分点。

继续原有 RL 训练
+0.49 pp
额外计算量超过对照方案的三倍
扩展至 400 个可验证环境
+3.37 pp
六项推理评测的平均提升

该结论来自特定小模型实验，不能直接外推到 Kimi 3T 级 MoE 或任何新的基础模型。

环境的核心价值是提供有效的学习信号：任务全部成功时，奖励失去区分度；任务全部失败时，同样不容易获得有用的策略梯度。合适的难度、可靠验证器和足够广的任务分布会显著影响训练成效。

RL 效果 = f(训练计算量，基础模型，环境覆盖，奖励质量，优化算法)

1.4 研究一结论

RL 确实构成可研究、可度量的后训练 Scaling 方向，但没有证据支持一种适用于所有模型与任务的「每增加一单位 RL FLOPs 都能持续获得固定收益」的规律。

更合适的工程实验是：固定基础模型与评测，在相同预算下比较增加 RL Compute、扩大环境覆盖和增加 Test-time Compute，测量端到端任务完成率以及每次成功的计算成本。

02 · 长程 Agent 的主要瓶颈是什么？

长程任务失败至少分为：基础能力不足、局部错误累积、历史状态退化。后两者非常重要，因为即使单步质量不变，任务成功率也会随步骤数下降。

失败类型表现主要原因
能力不足单独执行某一步也做不对知识、推理、工具掌握不足
错误累积每一步貌似合理，最后任务失败局部错误没有被及时发现或修复
状态退化最初正确，越执行越偏离目标错误假设、计划和中间结果被持续沿用

需注意：任务越长失败越多，本身不构成「状态退化」的充分证据；严格分析应与基于短步骤成功率构建的数学基线对比。

2.2 错误恢复能力比单步准确率更值得优化

使用独立步骤、最多一次修复且修复不引入额外错误的简化模型：

peffective = p + (1 − p)dr

其中 p 为单步直接正确率、d 为失败检测概率、r 为检测到失败之后的修复成功率。取 p=0.98、d=0.9、r=0.8，可得 peffective=0.9944。

AgentDebug（2025）对规划、动作、反思、记忆和系统操作错误进行分类，使用定位关键错误和有针对性的反馈来修复轨迹，在其测试任务中报告最高约 26% 的任务成功率相对改善。它支持「错误定位和恢复可提升 Agent 质量」的研究方向，但不是跨基准的通用增益。

2.3 长程 Agent 必须区分四层状态

100 万 Token Context 只增加历史内容的可访问范围，无法保证任务状态或真实环境一定正确。为工程分析，建议拆分：

L1 · Conversation / Context
历史消息、工具输出、推理记录与 KV Cache
↓
L2 · Task / Belief State
进度、已验证事实、暂时假设、子任务依赖和当前计划
↓
L3 · Environment State
文件、数据库、进程、Git 工作区、仿真器状态
↓
L4 · Policy State
模型参数与当前策略版本；决定下一步行动的策略

此四层模型是工程分析框架，不是 Kimi 技术报告原有的正式分类。

L1 决定能否访问历史；L2 决定是否正确理解进度；L3 决定能否恢复真实环境；L4 决定策略升级后如何解释和利用旧轨迹。仅保存 L1 并不能恢复 L3。

2.4 Kimi K3：跨训练迭代存活的 Partial Rollout

K3 技术报告 §4.1.2 与 §5.3 描述，当批次中一定比例轨迹完成，系统便暂停剩余轨迹、开始策略优化，并在后续训练迭代恢复尚未完成的轨迹。

因此，一条长轨迹可能由旧策略 πt 开始，后续在策略 πt+1 下继续。这会带来 Off-policy Staleness（策略版本滞后）的训练稳定性问题。K3 报告称通过 per-token regularization 处理此类情况，但不意味着任意跨版本长程 Rollout 都已解决稳定性问题。

2.5 长程能力瓶颈的优先级

优先级潜在瓶颈重点方向
1错误状态持续传播状态验证、根因定位、回滚
2环境反馈不足或错误可验证任务、可靠 Verifier
3缺少足够长的真实交互训练Long-horizon RL、任务分阶段设计
4Context / KV 成本过高缓存分层、状态恢复与压缩
5过度探索导致执行成本失控动态预算、停止策略、调度优化

这是一份面向长程工具使用型 Agent 的工程排序，并非已在所有 Benchmark 上验证的普适瓶颈排名。METR 的 Task-completion Time Horizon 可辅助衡量长程能力变化，但衡量的是人类完成任务所需时间对应的任务跨度，而不是 Agent 自己运行了多久；对很长的人类任务时长的外推也有统计局限。

03 · Agentic RL 的计算与网络架构

3.1 从 GPU 利用率转向端到端有效吞吐

传统训练主要执行 Forward → Loss → Backward；Agentic RL 则需要在模型推理、外部环境、验证反馈和训练更新之间反复迭代。

定义 Rollout GPU 的完整轨迹产出上限 XR、Sandbox + Verifier 能支持的上限 XE、Training GPU 能消化的上限 XT，在忽略额外同步损失的理想稳态：

Xtrain ≤ min(XR, XE, XT)

若进一步关注成功任务轨迹的吞吐，可以定义 Xsuccess=Xtrain × Ps。不过，RL 也从失败轨迹中学习，所以成功轨迹的数量不能独自衡量训练样本价值。

三种资源组织形式

类型设计方式优点主要代价
Co-locatedTraining 和 Rollout 复用 GPU共享资源、减少某些模型状态搬运训练与生成互相等待、HBM 竞争

K3 技术报告描述了 Co-located RL 与 Partial Rollout 的使用方式，但这不构成 Co-located 普遍优于分离式方案的证明。

3.2 两篇系统论文：AReaL 与 VenusRL

AReaL · 异步训练系统
最高 2.57×

Rollout Worker 持续生成，Training Worker 获取足够样本后更新；使用策略版本控制与适配的 PPO 处理陈旧数据。为特定基准下的加速结果。

VenusRL · 完全分离式 Agentic RL
最高 4.24×

在特定 32-GPU Qwen3-4B/32B 测试环境中报告端到端加速；另报告环境成本降低 89%，均不可直接线性推广。

AReaL（2025）说明打破同步等待有机会提升训练速度。VenusRL（2026-10-02，预印本）进一步指出：GPU Token 吞吐最高，并不代表 RL Update 最快。

例如，一次策略更新需要凑齐 32 组轨迹，若调度器平均推进数百条轨迹，却迟迟无法让其中 32 组完整结束，训练更新仍然受阻。优先完成临近结束的任务组，有时比最大化瞬时 Token/s 更有价值。

VenusRL 采用 Critical-group Scheduling，将组完成优先级、KV Cache 驻留和 Sandbox 资源调度结合。其结果提示：调度器应当理解 RL 的依赖关系，而不仅是单个推理请求长度。

3.3 五类不同的关键通信

流量类别数据内容流量特征网络目标
A · Policy TrainingGradient、Activation、MoE Tokens同步性强、持续、高密度高带宽、低延迟与低尾延迟
B · Policy Sync训练后的模型权重体量大、可能周期性分发高吞吐分发、版本一致性
C · Rollout StateKV Cache、KDA State不规则、动态且可能突发缓存亲和、迁移带宽、恢复时间
D · Agent EnvironmentRPC、文件、进程和 Sandbox 状态CPU/存储混合，工具交互驱动可靠性、响应时间和存储吞吐
E · Trajectory / RewardToken、Action、Reward、Logprobs批量或流式，数据相对结构化端到端吞吐、样本版本一致性

A：训练通信——传统高性能 Fabric 仍重要

TP、EP、PP、DP 的通信要求不会因为采用 RL 消失。模型内分片、专家 Token 分发和梯度同步仍会给 Scale-up/Scale-out Fabric 带来持续压力。

B：权重同步——分离式 RL 的潜在大流量

若以 K3 约 2.8T 总参数、完整 BF16 权重计算逻辑总量：

Sweights = 2.8 × 1012 × 2 Byte = 5.6 TB

该数字是全模型逻辑权重大小，不代表单 GPU 需要传输 5.6 TB，也不代表每轮同步都要搬运完整模型。真实传输取决于权重分片、量化、复制副本、增量同步以及 Worker 拓扑。

工程推断：随着参数增大与 Policy 更新频率上升，完全分离部署必须认真权衡权重分发成本。因而无法预先认定 Disaggregated 一定优于 Co-located。

C：KV Cache / Rollout State——恢复突发

K3 报告描述了 GPU KV Cache 与 CPU DRAM 外部缓存池协作的 Write-back 机制，用于保留长轨迹 Prefix，避免恢复时重新执行昂贵 Prefill。

对一个普通 GQA 模型，单 Token KV Cache 大小可近似写为：

MKV/token = 2 × L × HKV × Dh × B

例如 L=64 层、HKV=8、Dh=128、BF16=2 Byte：

MKV/token = 256 KiB；128K Token ≈ 32 GiB

此例仅适用于标准 GQA 的容量估算，不能直接用于 Kimi K3 的 MLA/KDA 混合缓存格式。

对于跨节点恢复，网络带宽更应由「实际搬运状态量／允许恢复窗口」估算：

BWrequired ≈ Nresume × Srestore / Trestore

举例：32 条轨迹同时恢复、每条搬运 2 GiB、目标 4 秒内完成，则需要 16 GiB/s（约 137 Gb/s） 的有效数据吞吐，尚未包括协议开销。

这是条件示例，不是 Kimi 的网络实测。恢复阶段的数据是否经由网络、远程搬运多少、是否有足够本地缓存，取决于实际系统部署。

与 Prefill/Decode Disaggregated Inference 不同，长程 RL 还需要考虑跨训练迭代的缓存持久化、恢复和策略版本切换。

D：Sandbox——独立的大规模计算与状态层

K3 的 AgentENV 使用基于 Firecracker 的 microVM，支持 Pause、Resume、Fork，以及内存/存储共享。报告称在 K3 训练和评估期间累计创建逾 5,100 万个 Sandbox 实例。

VenusRL 还使用 Mooncake Transfer Engine 来迁移 Sandbox Memory State。这里迁移的是 Sandbox 内存状态，不能与推理系统里 Mooncake 的 KV Cache 迁移混为一谈。

两者共同反映的系统需求是：将需要长期保存的执行状态与当前计算节点适度解耦，并在需要时低成本恢复。

图中是逻辑资源池，物理上可以共址、弹性共享或跨节点部署，不意味着固定需要三套独立集群。

原则一：模型并行组内部继续优化高密度、紧耦合的通信，例如训练 TP/EP，以及 Rollout 推理本身的模型分片通信。

原则二：资源池之间以调度解耦、状态迁移、模型同步和批量数据交换为主；不应无证据地把所有 GPU 与 CPU Sandbox 纳入同一个直接 Load/Store 域。

3.5 如何比较部署模式的经济性？

Ceffective = (CGPU + CCPU + Cnetwork + Cstorage) / Neffective

Neffective 应明确定义为满足质量标准的有效训练样本或最终成功任务，不同目标下不可混用。

工程倾向：Elastic Hybrid 值得作为参考方向，因为它允许根据瓶颈弹性切换资源；但目前并没有跨规模、跨模型的公开证据证明它普遍最优。

随着 RL 规模扩大，系统瓶颈可能从基础模型推理能力，转向可验证任务和奖励质量，再转向长程 Rollout、环境状态恢复以及 GPU/CPU 协同利用率。瓶颈并不固定在某一类计算资源上。

05 · 最终研究判断与下一步

判断一：RL Scaling 有效，但环境质量可能比额外计算量更加稀缺。ScaleRL 证明了条件性可预测性，RLVE 展现了环境扩展的潜在价值；尚不能将这些结论当作跨所有模型的普适规律。
判断二：长程 Agent 的提升越来越依赖状态管理和恢复。增加 Context、Thinking Tokens 与操作步骤都可能有用，但未解决错误假设持续传播时不保证有效。
判断三：Agentic RL 集群的异构性将更强。需要将 Policy Sync、KV/State、Sandbox 状态、轨迹数据与传统训练通信分别建模，才能解释真实的瓶颈及网络需求。

建议的后续工程研究：建立 Agentic RL End-to-End Traffic Model，按训练更新频率、Rollout 长度分布、Sandbox 执行/等待比例、Prefix 命中率、状态迁移与策略同步等变量，推导负载矩阵、并发、Burst、P99、资源利用率，以及 Co-located / Disaggregated / Hybrid 的成本边界。

后训练改变的不只是模型能力的形成方式，还可能改变 AI 数据中心中计算、内存、存储和互联网络的资源组织方式；但它并不能自动证明预训练负载将被替代，或所有资源都需要处于更大的物理 Scale-up Domain。
